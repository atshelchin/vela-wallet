# Codebase Survey: Rust Core Candidates (2026-07-28)
Produced by a 9-agent parallel survey of vela-wallet (8 area readers + synthesis). Feeds `spec.md`; T0 = v1 scope, T1/T2 = follow-up features.

## T0
- src/services/eth-crypto.ts — keccak256 / CREATE2 / EIP-55 checksum / functionSelector / ABI word-encode via alloy-primitives — a hand-written Keccak-f[1600] in TS with a parallel hand-rolled Swift copy (EthCrypto.swift) underlies every address and hash in the wallet; this is the foundation everything else in the crate builds on.
- src/services/hex.ts + src/services/sha256.ts — hex/base64url codecs, toQuantity JSON-RPC canonicalization, SHA-256 via the sha2 crate — foundational riders: single-sources the geth leading-zero quantity rule (already duplicated in safari-extension protocol.js) and the WebAuthn clientDataHash; fromHex's silent junk-acceptance fixed for free.
- src/services/safe-address.ts — counterfactual Safe + splitter CREATE2 math, saltNonce, setupData, MultiSend tx encode — the user's identity across 12 chains, currently triple-maintained (TS, SafeAddressComputer.swift, and byte-match constants in vela-relay); highest-severity silent-fund-loss surface in the repo.
- src/services/eip712.ts — hash_typed_data(json) via alloy-dyn-abi TypedData + a thin ensureDomainType shim — the exact digest the passkey signs for eth_signTypedData; also retires clear-signing.ts's drifting buildEncodeType copy (throw vs silent-'' divergence) by construction.
- src/services/attestation-parser.ts — DER→raw r||s with low-s normalization (der/ecdsa crates) + CBOR/COSE public-key extraction (ciborium/coset) — der runs on EVERY tx signature and COSE extraction derives the Safe address at onboarding; replaces ~380 lines of bespoke byte parsing with audited decoders and fixes the definite-length-only CBOR gap.
- src/services/p256-recovery.ts — two-assertion P-256 public-key recovery via p256 crate RecoveryId::trial_recovery — retires the largest hand-rolled crypto in the repo (BigInt Jacobian EC math) plus its documented Hermes perf pain; custom surface shrinks to ~50 lines of candidate-intersection + WebAuthn signing-hash assembly.
- src/services/webauthn-verify.ts (+ duplicate validateCreateClientData in public-key-upload.ts) — validate_client_data(kind, bytes) mirroring the Safe contract's byte-level acceptance rules — tiny rider that unifies two duplicated prefix/UV-flag checks into one contract-mirror.
- src/services/abi-decode.ts — decode_calldata / selector matching via alloy-dyn-abi + alloy-json-abi — the trust root of clear signing (what the user reads before approving); wrapping alloy's fuzz-tested dynamic-offset decoder costs near-zero Rust work and deletes a known past bug class (nested-tuple relative offsets).

## T1
- src/services/safe-transaction.ts (pure kernels only) — calculateSafeOpHash, WebAuthn contract-signature ABI assembly, EIP-1271 message hash, MultiSend packing, buildInitCode, in-band fee math — what the passkey signs and the calldata that moves money; port must carry the un-padded estimateInBandBasisGas charge basis (unwired fix from commit 2626474), not the padded-limit×3 behavior; async orchestration stays TS.
- src/services/approval-guard.ts — never-unlimited approval detection + calldata word-splice rewrite with typed U256/U160 caps — drainer defense with a natural property-test suite (rewrite never touches bytes outside the amount word; output always < cap).
- src/services/tempo.ts — Tempo reimbursement/settlement-split/fee math + constants contractually duplicated in vela-relay/shared/tempo.ts — turns 'MUST match' comments into one crate the bundler consumes natively; already caused a real incident (reimbursed<cost, 2026-07-07).
- src/services/eip681.ts — toBaseUnits/fromBaseUnits exact decimal kernel + EIP-681 URI parse/build — the canonical human→uint256 amount conversion feeding Send, QR, batch-send, and getvela.app /pay; Rust version rejects (not truncates) excess precision and validates digits.
- src/services/walletpair-protocol.ts (pure kernel) — pairing-URI, HKDF key schedule, AEAD framing with sequence nonces + replay window, canonical MessagePack JSON profile — maps onto chacha20poly1305/x25519-dalek/hkdf/rmp; one impl for wallet + any future dApp-side/SDK peer; WalletPairSession WebSocket layer stays TS.
- src/services/sim-assets.ts + transfer-monitor.ts decodeTransferLogs — unified Transfer-log decoder, asset-delta netting, revert-reason (Error/Panic) decode, bigint amount formatting — retires the in-repo fork of TRANSFER_TOPIC slicing between signing preview and incoming-transfer monitor; also serves token-autoadd.
- src/services/abi.ts — Multicall3 aggregate3 + balance/quote/Chainlink enc-dec via alloy sol!-generated types — every displayed balance/price/quote flows through hand-computed dynamic-tuple offsets today; compile-time-checked layouts in Rust.
- unit formatting trio: src/services/format-eth.ts formatWeiToEth + getvela.app/src/routes/api/wallet/+server.ts formatTokenBalance + wallet-api formatRawBalance — one format_units/parse_units from bigint (never f64) — the only way to reach the byte-identical copies drifting across repos (vela-bundler, deployer-api, getvela.app).
- src/services/batch-send.ts — split/sweep call shaping, gas/fee-token reserves, sumSplitBaseUnits — payroll pays up to 60 recipients in one signature; rides on the eip681 decimal kernel and deletes the second independent encodeErc20Transfer.
- src/services/siwe.ts — EIP-4361 parser with the url crate + a fuzz target over the message grammar — purely adversarial-input parsing that has already needed two security patches (userinfo trick, trailing-CR anchor).

## Explicitly rejected (do not port)
- src/services/selector-registry.ts — network orchestration end-to-end; the pure kernel (normalize + dedupe merge) is ~10 lines, too small to justify an FFI crossing
- src/services/local-descriptors.ts — configuration data, not logic; ship as embedded/loaded JSON the Rust clear-signing resolver parses — transliterating 500 lines of descriptor literals into Rust structs makes adding a protocol a recompile-everything chore across three binding targets
- src/services/public-key-upload.ts + public-key-index.ts — retry/idempotency/pending-queue orchestration around fetch and storage (issue #89 walletRef gate); porting moves state-machine risk into FFI for zero correctness gain
- src/services/bundler-service.ts (as a module) — fetch/cache/sponsorship I/O; the parseBundlerUnderfunded fragility is real but the fix is a structured error contract shared with vela-relay, not porting the wording regexes; only underfundedRequiredWei scaling rides into the units module
- src/services/tx-reconciler.ts — its value is JS-runtime-specific concurrency/throttle/persistence behavior; a Rust rewrite gains nothing and risks regressions on a ~10-line pure mapping
- src/services/wallet-api.ts — chain-fanout orchestration with caching/progress callbacks; its float math feeds display only, and its ABI helpers come along free when abi.ts moves
- src/services/token-autoadd.ts — becomes a one-line consumer of the Rust deriveAssetDeltas; the storage/metadata orchestration must stay platform-side
- src/services/currency.ts / fiat-fx.ts / currency-catalog.ts — async seed/rate-source orchestration, a 10-line validated parser, and a static data table; pure display bits ride only if formatNumber ever lands in the crate
- packages/vela-sdk/src/protocol.ts — 80 lines of dependency-free validation consumed by third-party web dApps that will not load wasm; Rust adds distribution friction without removing meaningful risk — keep as the shared TS package it already is
- chrome-ext-webauthn-proxy/webauthn.js codec — the extractable kernel is only a base64url codec and MV3-popup wasm is heavy; a shared JS module serves as well (noble already covers the actual P-256 there — audited, neutral trade)
- src/services/recipient-risk.ts — pure part is one EIP-7702 regex; the value is I/O orchestration and caching policy
- src/services/favicon.ts / avatar-style.ts — trivial or cosmetic; binding overhead exceeds the function bodies

## Crate API sketch (T0)

```
Single crate `vela-core`, bindings behind features (`uniffi` via proc-macros for Kotlin/Swift + uniffi-bindgen-react-native; `wasm` via wasm-bindgen). All FFI types are plain data: String, Vec<u8>, u64, flat records, and a flat `CoreError` enum (uniffi Error). Lean on: alloy-primitives (keccak256, Address/EIP-55, U256, CREATE2), alloy-dyn-abi + alloy-json-abi (calldata decode, EIP-712 TypedData), sha2, p256 + ecdsa (der parsing, low-s, RecoveryId::trial_recovery), ciborium + coset (attestation CBOR/COSE). Later waves add chacha20poly1305/x25519-dalek/hkdf (walletpair) and rust_decimal (amounts). Do NOT hand-roll any primitive.

Module layout:
  vela_core::primitives  — hex/base64url/quantity/hash
  vela_core::abi         — calldata decode + word encode (alloy-dyn-abi wrapper)
  vela_core::eip712      — typed-data hashing
  vela_core::safe        — counterfactual address math (T1 adds safe_op hash/signature assembly)
  vela_core::webauthn    — attestation parse, DER, client-data validation, P-256 recovery

Example signatures (T0):
  // primitives
  fn keccak256(data: Vec<u8>) -> Vec<u8>;                          // 32 bytes
  fn sha256(data: Vec<u8>) -> Vec<u8>;
  fn checksum_address(address_hex: String) -> Result<String, CoreError>;   // EIP-55
  fn function_selector(signature: String) -> Vec<u8>;              // 4 bytes
  fn create2_address(deployer_hex: String, salt: Vec<u8>, init_code_hash: Vec<u8>) -> Result<String, CoreError>;
  fn to_quantity(value: String) -> Result<String, CoreError>;      // canonical 0x-quantity, geth-safe
  fn to_base64url(data: Vec<u8>) -> String;  fn from_base64url(s: String) -> Result<Vec<u8>, CoreError>;

  // abi
  struct AbiValue { kind: String, value: String, children: Vec<AbiValue> }   // FFI-safe decoded tree
  fn parse_signature(sig: String) -> Result<String, CoreError>;              // canonical form
  fn decode_calldata(canonical_sig: String, calldata: Vec<u8>) -> Result<Vec<AbiValue>, CoreError>;

  // eip712
  fn hash_typed_data(typed_data_json: String) -> Result<Vec<u8>, CoreError>; // 32 bytes; ensure_domain_type shim then alloy TypedData

  // safe
  struct SafeAddressInfo { address: String, salt_nonce: String, setup_data: Vec<u8>, init_code_hash: Vec<u8> }
  fn compute_safe_address(pub_key_x: Vec<u8>, pub_key_y: Vec<u8>) -> Result<SafeAddressInfo, CoreError>;
  fn compute_splitter_address(owner_hex: String) -> Result<String, CoreError>;

  // webauthn
  struct P256PublicKey { x: Vec<u8>, y: Vec<u8> }
  struct WebAuthnAssertion { authenticator_data: Vec<u8>, client_data_json: Vec<u8>, signature_der: Vec<u8> }
  enum ClientDataKind { Create, Get }
  fn extract_attestation_public_key(attestation_object: Vec<u8>) -> Result<P256PublicKey, CoreError>;  // ciborium+coset
  fn der_signature_to_raw_low_s(der: Vec<u8>) -> Result<Vec<u8>, CoreError>;                           // 64B r||s, RIP-7212-ready
  fn validate_client_data(kind: ClientDataKind, client_data_json: Vec<u8>, expected_challenge: Vec<u8>) -> Result<(), CoreError>;
  fn recover_public_key_from_assertions(a: WebAuthnAssertion, b: WebAuthnAssertion) -> Result<Option<P256PublicKey>, CoreError>;  // p256 trial_recovery + candidate intersection

Testing: port the existing golden vectors from src/__tests__/services/{eth-crypto,abi-decode,eip712,safe-address,attestation-parser,p256-recovery,webauthn-verify,hex}.test.ts as Rust #[test] fixtures (cross-implementation conformance suite for free), plus proptest for hex/base64url round-trips, checksum idempotence, DER edge lengths, and quantity canonicalization. During rollout, run TS and Rust side-by-side behind a dev flag and diff outputs before deleting the TS paths.
```

## Integration constraints per binding route

(1) uniffi-bindgen-react-native (iOS/Android, RN 0.83 / Expo 55 / Hermes): android/ and ios/ are GITIGNORED — all native wiring must live in an Expo config plugin; imitate plugins/with-native-modules.js (withDangerousMod copies sources, patches MainApplication.kt/pbxproj/gradle). Existing modules are old-arch RCTBridgeModule style, but ubrn emits new-arch TurboModule C++/JSI, so the plugin must additionally inject a cargo-ndk gradle task and an xcframework link/run-script Xcode phase — materially more build machinery than today's copy-files approach; budget for it. Hermes has NO WebAssembly, so wasm is never a native fallback. (2) wasm-bindgen web: metro.config.js is stock — .wasm is not in assetExts; either add it plus an async init() gate before first crate call, or embed the wasm as base64 for zero config. Web export is `expo export --platform web` + scripts/fix-cf-pages-assets.js — verify CF Pages asset pathing once .wasm appears. getvela.app (SvelteKit on CF) can consume the wasm directly and drop viem from its client bundle. (3) Safari-extension inpage.js and src/modules/webview/injected-provider.generated.ts run as dependency-free single-file MAIN-world scripts — wasm is effectively unusable there; share policy (method classification allowlists, quantity rules) via JS tables CODEGEN'D from the Rust source, not the binary. Same constraint for third-party consumers of vela-sdk. (4) Kotlin/Swift direct: the crate's .xcframework/.aar follows the same copy-at-prebuild config-plugin route; targets/safari (@bacons/apple-targets) proves multi-target Xcode wiring already works in this repo. (5) Cross-repo: vela-relay/bundler can consume vela-core natively — tempo constants, in-band fee formulas, splitter creation-code/salt become one source of truth; the parseBundlerUnderfunded string-matching coupling should eventually be replaced by a structured error codec in the shared crate, not ported regexes. (6) chrome-ext-webauthn-proxy MV3 popup: wasm too heavy for an 80-line base64url codec — share a plain JS module instead.

## Per-area raw candidate notes

### hex-hash-abi
All files read in full. Key structural finding: the natural Rust unit is not per-file but one "eth-primitives" module = hex.ts + sha256.ts + eth-crypto.ts + abi.ts + abi-decode.ts (~1400 lines TS, four of five already unit-tested under src/__tests__/services/, giving ready-made cross-check vectors for the port). The honest Rust story is WRAPPING audited crates (tiny-keccak/sha2/alloy-primitives/alloy-dyn-abi), not reimplementing — the current codebase hand-rolls Keccak, SHA-256, and a dynamic ABI decoder, and eth-crypto.ts explicitly mirrors a second hand-rolled Swift copy (EthCrypto.swift), which is exactly the drift uniffi bindings would eliminate. Cross-surface duplication in packages/ is thinner than expected: safari-extension only duplicates quantity normalization (toHexChainId in packages/safari-extension/src/lib/protocol.js); vela-sdk/protocol.ts has no crypto. selector-registry and local-descriptors should stay in TS (I/O and config data respectively).
- **src/services/eth-crypto.ts** (score 9, pure): keccak256/keccak256Hex (hand-rolled Keccak-f[1600] on BigInt lanes), functionSelector, create2Address, checksumAddress (EIP-55), abiEncodeAddress/abiEncodeUint256/abiEncodeUint256Hex/abiEncodeBytes32
  - why: This is the strongest candidate in the area: create2Address computes the wallet's own counterfactual Safe address and checksumAddress renders every address the user sees, all on top of a hand-rolled Keccak that today exists in at least two parallel implementations (this TS file + iOS EthCrypto.swift). A single Rust impl backed by audited tiny-keccak/alloy-primitives replaces both hand-rolled hashes, kills the cross-language drift risk, and is dramatically faster than BigInt-lane Keccak on Hermes.
  - risk if wrong: Wrong CREATE2 address = wallet created at / funds sent to an address the user cannot control; wrong checksum/selector = mis-rendered or mis-targeted calls. Silent, catastrophic, money-losing.
- **src/services/abi-decode.ts** (score 8.5, pure): parseSignature/canonicalize/computeSelector/matchSelector/decodeCalldata plus the internal decodeTupleParams/decodeType/decodeDynArray dynamic-offset machinery
  - why: This decoder is the trust root of clear signing: what it decodes is what the user reads before approving a dApp tx. Hand-rolled dynamic-offset ABI decoding is exactly the kind of code alloy-dyn-abi/alloy-json-abi already does correctly and fuzz-tested in Rust; porting removes an entire class of offset/nested-tuple bugs rather than rewriting a solved problem (the Rust side would wrap alloy, not reimplement).
  - risk if wrong: SigningSheet shows the wrong amount/recipient/spender for a swap or approve — user knowingly approves a tx whose display lies to them. Worse than blind signing because it manufactures false confidence.
- **src/services/sha256.ts** (score 7.5, pure): sha256 (hand-rolled FIPS 180-4, single exported function)
  - why: Feeds the WebAuthn/passkey signature-assembly path (clientDataHash), so a bug corrupts signatures. In the Rust core it becomes one line over the audited sha2 crate — the hand-rolled JS (with its Math.floor 64-bit length split) disappears entirely, and it comes along for free once keccak moves. Low standalone value, high value as part of the same crypto module.
  - risk if wrong: Corrupted WebAuthn message hash → invalid P-256 signatures → UserOps rejected, or subtle divergence between platforms in the passkey flow.
- **src/services/abi.ts** (score 7, pure): encAggregate3/decAggregate3 (Multicall3), encBalanceOf/encGetEthBalance/encQuoteV3/encGetAmountsOut, decU256/decI256/decU8/decString (with bytes32-fallback UTF-8), decAmountsOut, decChainlinkUsd/decChainlinkAnswer
  - why: Every balance, token symbol, swap quote, and fiat price the app displays flows through these encoders/decoders. Hand-computed dynamic-tuple offsets (encAggregate3's h(0x60) head layout, decAggregate3's nested offset walk) are brittle by construction; in Rust these become alloy-core sol!-generated types with compile-time-checked layouts. Read-path only (goes into eth_call), so severity is display-corruption not fund-loss — hence below the signing-path files.
  - risk if wrong: Wrong balances/decimals/prices shown; a bad decAmountsOut or decChainlinkAnswer feeds a wrong quote into swap/fiat display, steering real user decisions with wrong numbers.
- **src/services/hex.ts** (score 6.5, pure): toHex/fromHex/addHexPrefix/stripHexPrefix/concatBytes/toBase64Url/fromBase64Url and especially toQuantity (JSON-RPC QUANTITY canonicalization, geth leading-zero rejection)
  - why: Foundation layer the whole crate needs anyway. toQuantity encodes a real interop landmine (geth rejects leading-zero quantities, ethers v5 emits them) and a lightweight variant is already duplicated in packages/safari-extension/src/lib/protocol.js (toHexChainId) — a shared Rust/wasm impl makes the canonicalization rule single-sourced across app, extension, and SDK. fromHex's parseInt silently accepts junk like 'zz'→NaN→0 today; a Rust port fixes that class for free. Individually trivial functions, which caps the score.
  - risk if wrong: Malformed quantity → dApp tx rejected by geth-family RPCs or, worse, a truncated/garbled value forwarded to eth_estimateGas; base64url bugs corrupt WebAuthn credential IDs.
- **src/services/local-descriptors.ts** (score 3, pure): KNOWN_CONTRACTS / LOCAL_DESCRIPTORS / interfaceDescriptor — ERC-7730-shaped descriptor data tables plus trivial lowercase-lookup accessors
  - why: Poor Rust candidate despite being pure: it is configuration data, not logic. If the clear-signing resolver moves to Rust, ship these tables as embedded JSON the Rust core parses — do not transliterate 500 lines of descriptor literals into Rust structs, which would make adding a protocol (the file's stated one-line workflow) a recompile-everything chore across three binding targets.
  - risk if wrong: Wrong descriptor field mapping mislabels a swap's pay/receive amounts on the signing sheet — but errors here are data-entry errors a rewrite does not prevent.
- **src/services/selector-registry.ts** (score 2, io-coupled): lookupSelector — parallel fetch of Sourcify-4byte/OpenChain/4byte.directory with cache and merge/dedupe
  - why: Not a candidate. It is network orchestration end-to-end; the only pure kernel (selector normalization + ordered dedupe merge, ~10 lines) is too small to justify crossing an FFI boundary. Keep in TS; the Rust core only needs the decode step it feeds (abi-decode).
  - risk if wrong: A wrong candidate signature is already defended against downstream — the caller keeps only the signature that decodes cleanly.

### passkey-webauthn
Strongest case in this area: a single rust crate module `webauthn` exposing parse_attestation_public_key, der_to_raw_low_s, validate_client_data, and recover_public_key_from_two_assertions — candidates #1–#3 share the same inputs (hex bytes in, bytes/structs out), are already covered by TS test fixtures that can be ported as Rust test vectors, and both hot paths (every signature via derSignatureToRaw in safe-transaction.ts; wallet-address derivation via extractPublicKey) are money-critical. Honesty note on 'multi-surface': the safari-extension and vela-sdk do NOT duplicate this logic today (signing is delegated to the app), so the sharing value is mainly app-native(Kotlin/Swift)+web-wasm from one implementation plus the chrome-ext-webauthn-proxy repo; the userHandle codec (#4) is the one真duplication with native Kotlin/Swift code. Key Rust guidance: do NOT hand-port the JS EC math — use p256/ecdsa/der/ciborium/coset audited crates; the custom surface shrinks to WebAuthn-specific glue.
- **src/services/p256-recovery.ts** (score 9, pure): recoverPublicKeyFromAssertions + entire hand-rolled P-256 stack: mod/modPow/modInv/sqrtP, Jacobian jAdd/jDouble/jMul, liftX, verifySignature, recoverCandidates, assertionSigningHash
  - why: This is a from-scratch ECDSA public-key-recovery implementation over NIST P-256 in JS BigInt. In Rust it collapses onto the audited `p256`/`ecdsa` crates (RecoveryId::trial_recovery covers recoverCandidates; only the two-assertion candidate-intersection and the WebAuthn signing-hash assembly stay custom, ~50 lines). That removes the highest-risk hand-rolled crypto in the repo and fixes Hermes BigInt slowness (the file already documents CI-timeout-grade perf pain that forced the Jacobian rewrite).
  - risk if wrong: This is the recovery escape hatch (issue #13): if the key index is lost, two passkey signatures rebuild the public key and hence the Safe address on-device. A math bug either returns null (user locked out of recovery, index becomes a SPOF again) or, absent the dual-verify guard, a wrong key → wrong Safe address → user 'recovers' into an empty wallet.
- **src/services/attestation-parser.ts** (score 9, pure): extractPublicKey (minimal hand-rolled CBOR walker + COSE key extraction: extractAuthData, extractP256FromCOSE, readCBORInt, readCBORByteString, skipCBORValue) and derSignatureToRaw + normalizeP256S (DER→raw r||s with low-s normalization for RIP-7212)
  - why: Two money-critical parsers written by hand. derSignatureToRaw runs on EVERY transaction/message signature (imported by safe-transaction.ts and p256-recovery.ts) — its DER walking has fragile edge handling (e.g. length-byte assumptions, >33-byte r/s not rejected explicitly) and its low-s normalization silently decides whether the RIP-7212 precompile accepts the sig. extractPublicKey runs once at wallet creation and its output DERIVES THE SAFE ADDRESS — a mis-parsed x/y is a permanently wrong address. In Rust: `der`/`ecdsa` crate for signature parsing, `ciborium`+`coset` for attestation/COSE, replacing ~380 lines of bespoke parsing with audited decoders. It also handles only definite-length CBOR ≤16-bit lengths; a spec-conformant authenticator using other encodings currently yields null.
  - risk if wrong: DER bug → signatures the P-256 precompile rejects (tx stuck) or, worse, malformed r/s accepted locally and submitted; CBOR bug → wrong public key → wrong Safe address minted at onboarding, funds sent to an address the passkey can never control.
- **src/services/webauthn-verify.ts** (score 6, pure): verifySafeWebAuthn (clientDataJSON prefix/suffix + authenticatorData UV-flag checks mirroring the Safe on-chain verifier); its twin validateCreateClientData lives duplicated in src/services/public-key-upload.ts
  - why: Small but it encodes the Safe contract's exact byte-level acceptance rules, and the same prefix-check logic is already duplicated in two files (get vs create prefixes). Folding both into one Rust `validate_client_data(kind, bytes)` alongside the attestation parser keeps the contract-mirror rules in one place across native/web/extension. Marginal on its own — worth taking only as a rider on candidate #2's crate.
  - risk if wrong: False pass → incompatible provider (e.g. Xiaomi Password Manager field order) mints a wallet whose signatures the Safe contract rejects forever; false fail → compatible devices blocked from onboarding.
- **src/modules/passkey/index.ts** (score 5, mostly-pure): Pure kernels only: encodeUserID/decodeUserName/decodeUserNameFromHandle (name\0uuid userHandle codec with UTF-8/UUID/printability validation, MAX_USER_NAME_BYTES), bufToHex/hexToBuf; NOT the register/sign/authenticate orchestration
  - why: The userHandle codec is a cross-platform wire format: iOS/Android native modules and web all mint `name\0uuid` and must decode it identically — today it exists in TS AND in the Kotlin/Swift native modules, exactly the divergence-prone duplication uniffi eliminates. decodeUserNameFromHandle's validation (fatal UTF-8, UUID shape, unprintable guard) prevents foreign-credential garbage becoming an account name pushed to the public index. Low complexity though, and the rest of the file (WebAuthn API calls, native module bridge, AbortController, dev override) must stay in TS.
  - risk if wrong: Divergent encode between platforms → wallet name lost/garbled cross-device; lax decode → attacker-shaped userHandle string flows into the account name and public key index (the mojibake and foreign-handle bugs the current guards were added for).
- **src/services/public-key-upload.ts** (score 2, io-coupled): uploadPublicKey/retryPendingUploads orchestration (create→verify→walletRef gate); only pure fragment is validateCreateClientData (covered under candidate #3)
  - why: BAD candidate as a whole: this is retry/idempotency/pending-queue orchestration around network and storage, with carefully tuned failure semantics (issue #89's walletRef gate). Porting it moves state-machine risk into FFI for zero correctness gain. Same verdict for public-key-index.ts (fetch client; addressToBytes32 is trivial). Listed to record the honest negative.
  - risk if wrong: Lost pending upload → key never indexed → no gas sponsorship / no cross-device recovery; but the risk lives in I/O sequencing, which Rust doesn't improve.

### signing-typeddata

In Rust it maps onto audited crates (chacha20poly1305, x25519-dalek, hkdf, rmp or a hand port) and one shared crate guarantees wallet, extension bridge, and SDK never drift on framing/canonicalization — the exact class of bug (non-canonical encodings, replay-window off-by-one, AAD field-order) that JS re-implementations drift on. ### cross-surface-and-integration
JS crypto/eth deps (package.json, read in full): NO viem, NO ethers in the app — crypto is @noble/curves ^1.9.7, @noble/hashes ^1.8.0, @noble/ciphers ^1.3.0, plus js-sha3 ^0.9.3 as a devDependency only (tests/scripts). Critically, keccak256 in src/services/eth-crypto.ts is HAND-WRITTEN (keccakF1600 in TS), not noble — the strongest single argument for a Rust core (alloy-primitives keccak/Address/CREATE2 replaces it). viem ^2.54.6 exists only in getvela.app/package.json (registry reads + getAddress); a wasm crate could drop it from the client bundle there. Rust should NOT reimplement what noble already covers well (P-256 verify, AES) — use audited k256/p256/RustCrypto crates via the bindings, or leave noble in place where it is the only consumer.

Integration constraints per binding route, from files actually read:
(1) uniffi-bindgen-react-native (RN 0.83, Expo 55, Hermes, expo-dev-client): android/ and ios/ ARE gitignored (.gitignore lines "/ios" "/android" under "generated native folders") — persistence MUST go through a config plugin. plugins/with-native-modules.js is the exact pattern to imitate: withDangerousMod copies module sources from modules/<name>/{ios,android} into the generated projects, patches the bridging header, registers Kotlin ReactPackages by string-editing MainApplication.kt, injects gradle deps into android/app/build.gradle, and addSourceFile()s into the pbxproj. (2) wasm-bindgen + Metro web: metro.config.js is stock getDefaultConfig (5 lines, zero customization) — .wasm is not in assetExts today; either add it (config change, low risk) plus an async init() gate before first call, or embed the wasm as base64 to stay zero-config.
