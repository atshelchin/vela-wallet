# Implementation Plan: Identicons in the shared Rust core

**Branch**: `003-rust-identicon` | **Date**: 2026-07-30 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/003-rust-identicon/spec.md`

## Summary

Add one module — `rust/crates/vela-core/src/identicon.rs` — that reproduces
`identicons-esm@1.0.1`'s identicon computation exactly, plus a generated sibling
`identicon_features.rs` holding the 84 section artworks as `&'static str`. The one
genuinely hard part is that the algorithm's hash ends in
`Number.prototype.toString(10)`, so the port needs ECMAScript's shortest-round-trip
float formatting, tie-breaking included; Phase 0 settled this on **`ryu-js`**, a
zero-dependency `no_std` crate written for exactly that purpose, after measuring
that Rust's own `std` formatter disagrees with V8 on tie cases (2 in 9,068). With
`ryu-js` in place, a full `make_hash` prototype matched the real JS package on
**200,026 of 200,026 seeds**, including 15,788 cases in the regime where JS itself
degenerates.

Performance falls out of three choices: the chaotic inner loop (100 float
iterations per distinct character, the dominant cost) is precomputed into a
**`const` lookup table at compile time** — verified bit-identical to the runtime
loop — so `make_hash` becomes one multiply-add per character; the artwork table is
`&'static str` in `.rodata`, so section selection is an array index with no
allocation; and SVG assembly does a single `String::with_capacity` of the exact
final length. The crate keeps **no mutable state at all**, which is how FR-008's
flat-memory requirement is met.

Distribution needs no new infrastructure: `app-desktop` is itself a Rust crate and
depends on `vela-core` directly; `app-ios`/`app-android` reuse the uniffi 0.32
shell and `app-web` the wasm-bindgen shell that feature 001 already built. All
decisions and measurements: [research.md](./research.md).

## Technical Context

**Language/Version**: Rust 1.97.1 (pinned by `rust/rust-toolchain.toml`), edition 2021, MSRV 1.85

**Primary Dependencies**: `ryu-js` 1.0.3 (new — ECMAScript-compliant `f64`→string, zero deps, `no_std`, no-alloc); `base64` 0.22 and `thiserror` 2 (already in `vela-core`). No other new dependency; `identicons-esm@1.0.1` stays a **dev-time oracle** (already in `package.json`), not a runtime dependency.

**Storage**: N/A (pure computation). The artwork table is generated Rust source; the conformance corpus is committed JSON.

**Testing**: `cargo test -p vela-core` (conformance corpus + unit + proptest); `cargo bench`-style criterion-free micro-benchmark behind `--release`; corpus generated by a Node script that imports the real `identicons-esm` package; replayed on Kotlin/Swift/wasm by the existing harnesses.

**Target Platform**: `app-desktop` (direct Rust dependency, GPUI), `app-ios` (Swift via uniffi), `app-android` (Kotlin via uniffi), `app-web` (wasm32-unknown-unknown via wasm-bindgen). Also the current Expo/RN app's web path.

**Project Type**: library module inside an existing multi-target Rust workspace

**Performance Goals**: < 2 µs (target < 1 µs) per identicon SVG from a 42-character address; at most one heap allocation per returned document; `make_hash` allocation-free

**Constraints**: bit-identical `f64` arithmetic across x86-64/aarch64/wasm32 — no FMA contraction, no fast-math, multiply order is contract; no mutable global state (FR-008); no `unsafe` in `vela-core` (crate-level `#![forbid(unsafe_code)]`); no `unwrap`/`expect`/`panic!` (crate-level `deny`); existing accounts' avatars must not change (release blocker)

**Scale/Scope**: one new core module (~450 lines) + one generated table (~90 KB of `&'static str`); 84 artwork fragments; 5 new binding exports per surface; ~200k-case conformance corpus

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

`.specify/memory/constitution.md` is still the unfilled spec-kit template — this
project has no ratified constitution. Applying spec-kit defaults in its spirit, and
the standing conventions feature 001 established for this crate:

- **Library-first**: PASS — the module is a standalone, independently testable part
  of `vela-core`; binding exposure and app migration come after it is green.
- **Test-first**: PASS — the conformance corpus is generated from the real JS
  package and committed before the app switches over; the corpus, not review, is
  what gates the migration.
- **Simplicity**: PASS — one module, one generated table, one new third-party
  crate. No new crates, no new binding routes, no state.
- **No hand-rolled primitives** (feature 001's FR-005, treated as a standing rule):
  PASS — the one primitive that would be dangerous to hand-roll here is
  ECMAScript float formatting, and it is delegated to `ryu-js` rather than
  reimplemented. See research D2 for the measurement that justifies it.
- **Typed errors, never a default value** (feature 001's FR-004): PASS — FR-004/005
  keep the safe default strict and put bug-compatibility behind an explicit mode.

**Post-Phase-1 re-check (2026-07-30)**: no new violations. One deliberate,
recorded deviation from "pure computation only" was considered and rejected — an
LRU cache inside the core — because it would contradict FR-008; caching stays with
the caller.

**Structure Decision**: one module in the existing pure crate, mirroring how
`primitives.rs`/`safe.rs` are laid out — no new crate, because nothing here needs a
different `crate-type` or binding technology. The artwork table is a *separate
generated file* rather than inlined into `identicon.rs` so that regenerating it
(FR-009) is a whole-file overwrite that can never disturb hand-written logic, and
so `identicon.rs` stays reviewable at ~450 lines instead of ~2,000.

The generator reads the artwork out of the **installed `identicons-esm` package**
(`node_modules/identicons-esm/core`), not out of a vendored copy, so "regenerate
and diff" is a real check against the dependency the app pins rather than against a
snapshot that could silently drift.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| New third-party dependency (`ryu-js`) in a crate that pins deps conservatively | The port's correctness hinges on ECMAScript `Number::toString` semantics, tie-breaking included. Measured: `std`'s formatter disagrees with V8 on 2/9,068 doubles (research D2) | Hand-rolling the ECMAScript algorithm on top of `std` needs exact bignum comparison to resolve ties — more code, and the *precise* class of hand-rolled primitive feature 001's FR-005 forbids. Accepting `std`'s 2/9,068 divergence was rejected: both cases fall outside the reachable value domain today, but "outside today" is not a guarantee, and this is the one computation whose silent failure is invisible |
| Two params functions (strict + JS-bug-compatible) instead of one | FR-004 wants a wallet-safe default; FR-005 wants the parity claim provable over the *whole* input domain, including seeds where JS emits `fill="undefined"` | A single strict function makes the 100% parity claim unverifiable in the degenerate regime. A single bug-compatible function puts the literal string `undefined` into a wallet's rendering path as the default. The two differ by ~5 lines |
| A `const fn` table of precomputed floats | It removes ~4,200 float ops per identicon (the dominant cost) with zero runtime state, zero lazy init and zero allocation — satisfying SC-004 and FR-008 together | Runtime memoisation needs either a lock or thread-local state (both mutable state FR-008 rules out); computing every time misses the SC-004 target. Const-eval float determinism was verified against the runtime loop for all 131 entries before adopting (research D4) |
