# Phase 0 Research: Identicons in the shared Rust core

**Date**: 2026-07-30 · **Method**: local differential experiments against the real
`identicons-esm@1.0.1` package, not doc reading. Every number below was produced by
running code: two throwaway Rust programs (`rustc`-compiled, `std`-only and
`ryu-js`), one 200,026-case Node↔Rust differential harness, and direct probes of the
package's exported functions. The library's original TypeScript was recovered from
its published sourcemaps and confirmed **byte-identical** to
`github.com/onmax/nimiq-identicons` at tag `v1.0.1` (`b920756`), so the port is
written against real source rather than decompiled bundle output.

## The algorithm, precisely

Reproduced here because the port's correctness is entirely in the details, and
because the JS source reads as if it were simpler than it is.

```text
makeHash(seed):
  acc = 0.5
  for each CODE POINT ch of seed:                 # JS for..of
     acc = acc * (1 - acc) * chaosHash(leadingCodeUnit(ch) + 3)
  full = reverse( acc.toString(10) )              # ECMAScript Number::toString
  pad  = full[5]  or  '0' if absent
  hash = full.replaceFirst('.', pad).slice(4, 21).padEnd(13, pad)

chaosHash(n):  a = 1/n;  100x { a = (1 - a) * a * 3.569956786876 };  return a

params(hash):
  main = hash[0]   background = hash[2]   accent = hash[11]
  face = hash[3..5]  top = hash[5..7]  sides = hash[7..9]  bottom = hash[9..11]
  # note: index 5 is deliberately read twice (once as a digit of `face`,
  # once as a digit of `top`) -- that is the upstream behaviour, not a typo.
  if main == background:            main = (main + 1) % 10
  while accent in {main, background}: accent = (accent + 1) % 10
  section index -> abs(idx % 21) + 1     # 1..21
```

Three separate places where a naive port silently diverges: the float-to-decimal
step (D2), the code-unit rule (D3), and the multiply order (D8).

## D1 — Behavioural oracle

**Decision**: `identicons-esm@1.0.1` exactly as pinned in `package.json`. The corpus
is generated by importing the **installed package** (`node_modules/identicons-esm/core`),
not a vendored snapshot.

**Rationale**: users already have the avatars this version draws; SC-003 forbids
changing them. Importing the installed package means "regenerate and diff" checks
the port against the dependency the app actually ships, so a future dependency bump
shows up as a corpus diff instead of passing silently.

**Verified**: the package's own inline test snapshots are reproduced by the port —
`makeHash('test') = "39522148458090"`, `makeHash('hello') = "7935187296325090"`,
`makeHash('NQ07 0000 …') = "113682528368518"`.

## D2 — ECMAScript `Number::toString(10)` (the load-bearing decision)

**Decision**: use `ryu-js`. Do **not** build the ECMAScript algorithm on top of
Rust's `std` float formatter.

**Rationale**: the hash's decimal *string* is what gets sliced, so the formatter is
part of the algorithm. ECMAScript specifies shortest-round-trip digits with an
explicit tie-break ("closest to x; if two are equally close, the even one"), plus a
switch to exponential form outside `-6 < n <= 21`. Rust's `{}`/`{:e}` also produce
shortest-round-trip digits, but resolve ties differently.

**Measured**: a hand-written ECMAScript formatter layered over `std`'s `{:e}` was
diffed against V8 over 9,068 doubles (the reachable hash domain, plus powers of ten,
exponent boundaries, subnormals and random bit patterns):

```text
std-based:  9,068 checked,  2 mismatches
  bits=430c6bf526340002   V8 1000000000000000.2   std 1000000000000000.3
  bits=42a3db4129c5e120   V8 10916206011120.562   std 10916206011120.563
ryu-js:     9,068 checked,  0 mismatches
```

**Alternatives rejected**:

- *Accept the `std` divergence.* Both failing doubles are outside the reachable
  domain (D7 proves the hash accumulator stays in `(0, 0.5]`; these are ~1e15 and
  ~1.1e13). But the argument is "unreachable today", not "unreachable", and this is
  precisely the computation whose failure nothing observes — a user would just see
  a different face. Rejected on the same grounds feature 001 rejected lenient
  parsing.
- *Hand-roll the tie-break.* Resolving a tie exactly requires comparing
  `2x` against `(2s±1)·10^(n−k)` in exact arithmetic — bignum, because the exponent
  reaches ±324. That is more code than the rest of the module and is exactly the
  "hand-rolled primitive" class feature 001's FR-005 forbids.

**End-to-end confirmation**: a complete `make_hash` prototype (chaos loop + code-unit
rule + `ryu-js` + string surgery) was diffed against the real package over a
200,026-seed corpus spanning hex addresses, mixed-case addresses, Nimiq addresses,
short/medium ASCII, BMP unicode, astral characters, control characters, and inputs
up to 3,500 characters:

```text
make_hash: checked 200026, 0 mismatches (15788 degenerate cases included)
```

## D3 — JavaScript string semantics

**Decision**: iterate Rust `char`s (= code points, matching JS `for..of`), but feed
the chaos function the **leading UTF-16 code unit**:

```rust
let cu = if cp <= 0xFFFF { cp } else { 0xD800 + ((cp - 0x10000) >> 10) };
```

**Rationale**: the JS source reads `ch.charCodeAt(0)` on a single-code-point string.
For BMP characters that is the code point; for astral characters it is the *high
surrogate*. So `"💎"` (U+1F48E) contributes `0xD83D`, not `0x1F48E`. Iterating
`char`s and using `ch as u32` diverges on every astral input — a bug that would
never show up in a hex-address test suite.

**Out of domain, by construction**: JS strings can hold lone surrogates; Rust `&str`
cannot. Seeds reaching the core are valid UTF-8, so the case does not arise; noted
so a future JSON/FFI path does not reintroduce it.

## D4 — Precomputed chaos table (`const fn`)

**Decision**: precompute `chaos_hash(n)` for `n = 0..=130` (i.e. code units
`0..=127`, the ASCII range every real seed uses) into a `static` table built by a
`const fn` at compile time. Non-ASCII code units fall through to the runtime loop.

**Rationale**: the 100-iteration loop is the whole cost of hashing — a 42-character
address costs ~4,200 float operations, versus ~42 multiply-adds with the table. A
compile-time table has no lazy-init, no lock, no thread-local, no allocation and no
mutable state, so it satisfies SC-004 and FR-008 simultaneously. Cost: 131 × 8 B =
**1,048 bytes of `.rodata`**.

**Risk and its retirement**: const-eval float arithmetic must be bit-identical to
runtime float arithmetic, or the table silently changes avatars. Verified by
compiling and running the comparison for every entry:

```text
const-vs-runtime bit differences: 0 / 131      (sample: chaos(123) = 0.8844062755976996)
```

A unit test asserts the same invariant permanently, so a toolchain change that broke
it would fail the build rather than change users' avatars.

**Alternatives rejected**: runtime `OnceLock` memoisation (mutable state, FR-008);
a full 65,536-entry table (512 KB of `.rodata` to serve inputs that never occur);
no memoisation (misses the SC-004 target for no reason).

## D5 — The two regimes where the JS library is itself broken

Both were confirmed by calling the package's exported functions directly, not by
reading the source.

**Regime A — three-digit exponent (`hash[0] == 'e'`).** Once `acc` drops below
`1e-100`, `toString` yields e.g. `1.6288638040436185e-108`; reversed, the leading
characters are `801-e…`, and `slice(4, 21)` starts *at the `e`*. So `main` parses as
`NaN`, `colors[NaN]` is `undefined`, and the template interpolates the literal text
`undefined`:

```text
seed 'x'.repeat(2000):  hash = e5816340408368826
                        colors = { background: "#88B04B", accent: "#1A5493" }   // main absent
                        assembled SVG contains "undefined" x2
```

Onset measured, for a seed of repeated `x`: exponential form begins at **93**
characters, the three-digit exponent — and therefore the breakage — at **1,836**.
The threshold is seed-dependent, since every character contributes its own decay
factor; over 200,000 random seeds the shortest trigger observed was **1,046** code
points. Either way, real seeds are 42 characters.

Crucially, this is the *only* corruption of the hash string. Across all 200,026
cases the sole non-digit position was index 0 and the sole non-digit character was
`e`:

```text
hash length distribution: 13:5361  14:3504  15:20677  16:35996  17:134488
non-digit positions:      {0: 15788}          non-digit chars: {'e': 15788}
```

So section indices and the other two colours stay valid; only `main` breaks.

**Regime B — seven-character decimal form (JS throws).** If `acc`'s shortest decimal
form is exactly 7 characters (e.g. `0.12345`, `0.00001`, `8.84e-7`), the `.` lands at
reversed index 5 and becomes the pad character. The hash then contains `.`, the
two-character section reads parse as `NaN`, and the library throws — confirmed
directly:

```text
sectionToSvg('face', NaN)  ->  Error: SVG file not found for face with index NaN/NaN.
```

Astronomically unlikely for a chaotic double (it needs ≤5 significant digits) and
absent from 200,026 samples, but structurally reachable, and a wallet core must not
panic on it.

**Decision**: two entry points, ~5 lines apart.

- `identicon_params` (**default, wallet-safe**): returns
  `Err(CoreError::InvalidIdenticonSeed)` in both regimes. Rationale: in Regime A the
  JS output is a black/invisible circle, which for an account avatar is worse than a
  loud failure; in Regime B the JS behaviour *is* a failure.
- `identicon_params_js_compat` (**parity proof**): errors only where JS throws
  (Regime B) and otherwise reproduces the malformed output byte-for-byte, emitting
  the literal `"undefined"` as `main`. This is what makes FR-002's parity claim
  provable over the entire input domain instead of only its well-behaved part.

The corpus records Regime A cases with a `divergence` note, following the convention
feature 001 established for intentional strictness changes.

## D6 — Artwork table representation

**Decision**: a generated `identicon_features.rs` with four `static [&str; 22]`
arrays (index 0 unused, so `1..=21` addresses directly). Generated by
`scripts/gen-identicon-features.mjs`, which imports `identiconFeatures` from the
installed package.

**Measured**: 84 entries — exactly 21 per section, indices 1..21 with no gaps;
**82,955 bytes** total, largest fragment 2,707 bytes.

**Rationale**: `&'static str` in `.rodata` means section selection is a bounds-checked
array index with zero allocation and zero initialisation, and the table is shared
across all threads and all binding surfaces for free. A generated file (rather than
inlining into `identicon.rs`) makes regeneration a whole-file overwrite that cannot
disturb hand-written logic.

**Alternatives rejected**: `include_str!` of 84 committed `.svg` files (84 new assets
to keep in sync, and the artwork is no longer visible in review); a runtime
`HashMap` keyed by the library's `./features/optimized/face/face_01.svg` path
strings (rebuilds a key string and hashes it on every render, for no benefit — the
key derivation is a pure function of section and index).

## D7 — Reachable value domain, and SVG capacity

**Measured** over every possible UTF-16 code unit (all 65,536):

```text
chaosHash range: min = 0.3425453163642803   max = 0.8924891966912822
values outside (0,1): 0
```

Since the maximum is < 1, `acc * (1 - acc) * chaos < acc` for every step: **`acc` is
strictly decreasing and stays in `(0, 0.5]`**, reaching 0.5 only for the empty seed.
That bounds the hash string at 17 characters (`slice(4, 21)`), which is why the hash
is carried in a `[u8; 17]` stack buffer with no allocation. It is also what makes
Regime A a long-seed-only phenomenon.

**SVG size, measured** over 3,000 addresses: stock output **2,218–8,358 bytes**; the
wallet's circular variant 2,253 bytes for the reference address. Assembly therefore
computes the exact final length by summing part lengths and does a single
`String::with_capacity` — one allocation per document, satisfying SC-004.

## D8 — Floating-point reproducibility

**Decision**: write the two expressions in exactly the source order the JS uses
(`(1.0 - a) * a * K` and `acc * (1.0 - acc) * chaos`), never `mul_add`, and add a
comment at each site saying the order is contract, not style.

**Rationale**: Rust does not perform FMA contraction or reassociation of float
expressions (no `-ffast-math` equivalent), and every target of interest (x86-64
SSE2, aarch64, wasm32) implements IEEE-754 binary64 exactly — so `f64` results are
bit-identical across all four platforms without special flags. The real risk is not
the compiler, it is a future reader "simplifying" the arithmetic. The conformance
corpus catches it; the comment prevents it.

**Confirmed**: the workspace `[profile.release]` (`lto = true`, `opt-level = "z"`)
contains no float-affecting flag, and the D4 experiment showed const-eval and
runtime agreeing bit-for-bit under `-O`.

## D9 — Seed normalisation policy

**Decision**: `normalize_seed` = **full Unicode lowercase**, then truncate to **128
UTF-16 code units**, returning `Cow<str>` (borrowed when already normalised — the
common case, since stored addresses are lowercase ASCII).

**Rationale**: the wallet's current `Identicon.tsx` does
`seed.toLowerCase().slice(0, 128)`, and that normalisation is part of "the same
logo", so it belongs in the core where all four platforms share it.

The first draft of this decision narrowed to **ASCII-only** lowercasing, on the
theory that matching JS `toLowerCase()` exactly would mean betting on Rust's and
V8's Unicode case tables agreeing for seeds that never occur. That reasoning was
wrong once measured — the bet is not a bet:

```text
per code point:  1,112,064 checked, 0 mismatches   (Rust char::to_lowercase vs V8)
string level:       41,586 checked, 0 mismatches   (incl. Greek final sigma,
                                                    U+0130 length expansion,
                                                    Deseret astral, fullwidth)
```

So the ASCII narrowing bought nothing and cost a real divergence. Full Unicode
lowercasing is used instead, with an ASCII fast path that borrows (so the address
case still allocates nothing). **Order matters**: JS lowercases *then* slices, and
lowercasing can change length (`U+0130` expands to two code points), so the port
does the same.

**Recorded divergence** (one, unreachable for address seeds): where JS's UTF-16
`slice(128)` splits a surrogate pair it keeps a lone high surrogate; Rust `&str`
cannot represent one, so the core drops that character. Reaching it needs a
>128-code-unit seed with an astral character at exactly the boundary.

**Verified end to end**: `scripts/verify-identicon-parity.mjs` compares the app's
pre-migration expression against the core over every 0x-address literal in the
repository (both cases) plus 200,000 random seeds — **200,478 byte-identical, zero
divergences**.

**Note**: with D5 returning a typed error for degenerate seeds, the 128 cap is no
longer load-bearing (Regime A starts at 1,046 characters). It is retained because
removing it would change avatars for >128-character seeds, and kept as
defence-in-depth.

## D10 — No cache inside the core

**Decision**: the core holds no cache. Callers cache; the app's existing bounded LRU
in `Identicon.tsx` is the right layer.

**Rationale**: FR-008. A cache in a pure core is the memory-growth risk the
requirement exists to prevent, and it would have to be either locked or
thread-local. With D4's table the hash is cheap enough that a cache buys
little — and callers that do want one (a list re-rendering the same 20 accounts) are
better placed to bound it.

## D11 — Nimiq address validation

**Decision**: port `ValidationUtils.isValidAddress` + the space-regrouping of
`validateInput` (Nimiq's 32-character alphabet `0123456789ABCDEFGHJKLMNPQRSTUVXY`,
36-character length check, and the mod-97 IBAN checksum), so `create_identicon`'s
full contract exists. Vela's own call sites pass `validate_address: false`.

**Rationale**: cheap (~40 lines), completes the port, and lets the corpus cover
`createIdenticon`'s validate-and-normalise path including the placeholder fallback.
Leaving it out would mean the one function users of the JS library actually call has
no faithful equivalent. It is *not* on Vela's path: EVM addresses fail Nimiq
validation, so enabling it would return the placeholder for every account.

## D12 — Loading an ESM-only oracle under jest (found during implementation)

**Problem**: routing the identicon through `src/services/vela-core` made every
importer of the facade — most of the app — transitively import `identicons-esm`,
which is ESM-only (no `require` condition in its exports map). ts-jest resolves
CommonJS with Node10 semantics, so **49 of 119 suites stopped running**.

**Decision**: transform the package rather than stub or exclude it —
`transformIgnorePatterns: ['/node_modules/(?!identicons-esm|@nimiq/utils)']`, a
`@babel/plugin-transform-modules-commonjs`-only transform for `.m?js` (no
`@babel/preset-env`, which is not installed and would only add cost), plus
`moduleNameMapper` and a tsconfig `paths` entry so both the runtime and the type
side can resolve the `./core` subpath.

**Rationale**: a `moduleNameMapper` stub would have been one line, but the JS path
is not dead code — it is what Hermes actually runs on iOS and Android until the
native rewrite lands. Stubbing it would make a broken native avatar invisible to
the suite. Making it genuinely loadable also unlocked
`src/__tests__/services/identicon.test.ts`, which replays the shared corpus through
the **native** path — a surface that previously had no runtime test at all (the
existing test reads the component's source as text).

**Cost**: full-suite wall clock 24s → ~27–30s. Baseline restored: 118 suites, 1,394
tests green, identical to before the feature.

## Measured results (recorded 2026-07-30, after implementation)

| Metric | Target | Measured |
|---|---|---|
| `identicon_svg_circular`, 42-char address | < 2 µs (target < 1 µs) | **0.323 µs** |
| `make_hash`, 42-char address | — | **0.183 µs** |
| Heap allocations per SVG | ≤ 1 | **1** (0 for `make_hash` and `identicon_params`) |
| Same work in the JS library | — | 0.841 µs / 0.639 µs → **~2.6× faster** |
| Artwork table | fixed, no heap | 82,955 B of `&'static str` in `.rodata` |
| Chaos table | fixed, no lazy init | 1,024 B in `.rodata` |
| Rust conformance | 100% | 1,499 cases + 20,000 bulk hashes green |
| Web (shipped wasm) conformance | byte-identical | 21,488 cases green |
| Live parity vs the shipped JS library | zero divergences | **200,478 seeds byte-identical** |

The JS comparison is against the library's *already optimised* path (it memoises
`chaosHash` and pre-groups the section arrays), so 2.6× is the honest margin over a
tuned baseline rather than over a naive one. The larger win is categorical: native
platforms have no JS engine on the rendering path at all.

## Open questions

1. **Should `app-web` (SvelteKit) and `app-desktop` (GPUI) adopt the core in this
   feature, or only the current Expo app's web path?** The plan wires the current
   app plus the binding exports; the four new platform shells are scaffolds
   (`app-desktop` is a Rust crate and can `use vela_core::identicon` directly, with
   no binding layer at all). Adoption there is a follow-up unless the requester
   wants it now.
2. **Does the circular variant belong in the core or in each platform's view layer?**
   The plan puts it in the core (FR-003) because it is what users see today and
   duplicating string assembly four times is the drift class this feature exists to
   remove. It is, however, presentation, and a reasonable reviewer could push back.
3. **Corpus size in the repository.** 200k cases with full SVGs would be tens of
   megabytes. The plan commits ~2,000 full-SVG cases plus ~200k hash/params cases as
   compact rows, and keeps the large-scale differential run as a regenerable script
   rather than committed data. Confirm that split is acceptable.
