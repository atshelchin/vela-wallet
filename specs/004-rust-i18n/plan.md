# Implementation Plan: i18n / L10n in the shared Rust core

**Branch**: `004-rust-i18n` | **Date**: 2026-07-31 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/004-rust-i18n/spec.md`

## Summary

Add one module tree — `rust/crates/vela-core/src/i18n/` — that reproduces
`i18next@26.3.1`'s resolution, interpolation, nesting and `defaultValue` semantics
exactly, plus `src/l10n/` for the number/date/time/currency layer. Phase 0 settled the
two decisions that looked hard and one that inverted:

**Plural rules cost nothing to hand-write.** The 15 shipped locales collapse to five
CLDR rule bodies — 110 lines, **1,204 wasm bytes**, cross-validated against the node
full-ICU oracle at **182,790/182,790, zero disagreements**. `icu_plurals` measured
**57,960 bytes** (48×) and would still have required a hand-written `f64`→operands
bridge, because `PluralOperands` has no `From<f64>`. This is the whole justification
for the feature: Hermes ships `Intl` *without* `PluralRules`, so ten Russian keys
render the wrong grammatical form on every native build today, and 1.2 KB of Rust
closes it permanently.

**Key bytes, not value bytes, are the memory problem.** Repeated per locale, the 1,141
dotted paths cost 460,471 bytes; interned once, 31,198 — a 14.8× collapse. So the
catalog splits in two: a **shared compiled-in path table** (1,205 paths + a 151-byte
branch bitmap) paid for once, and a **per-locale value blob** loaded on demand. That
lands `ja` + `en` at **126,352 bytes** against SC-005's 135,345 budget, with **21.1 ns**
lookups and **zero allocations**. The obvious flat `&[(&str,&str)]` array fails the
budget at 138,309; `serde_json` fails it 2.6× over at 348,649 *and* costs 4 allocations
per lookup.

**The measurement that inverted the plan: do not compile catalogs into the web
artefact.** The engine is nearly free at **+4,849 wasm bytes**. Catalogs are the entire
cost — all 15 measured (not extrapolated) at **1,315,023 bytes**, **315,023 over** the
`MAX_WASM_BYTES = 1_000_000` gate. Worse, embedding is *counterproductive over the
wire*: 15 locales ship as **176,852** brotli'd bytes of plain JSON against **+235,476**
for the best in-wasm variant, and base64-wrapping costs **+31.4%** on the currently
shipped module. So web loads per-locale JSON at runtime — which is also the only design
that delivers the on-demand requirement properly: a Japanese user fetches **15 KB**,
not a 15-locale blob. Compiled-in catalogs stay available behind per-locale cargo
features for desktop and native, where there is no wire.

Single-source-of-truth is preserved by the **generator**, not the linker: the corpus
moves to `rust/crates/vela-core/i18n/locales/`, and `scripts/gen-i18n.mjs` emits the
shared path table, the per-locale Rust tables, the per-locale JSON assets and the
TypeScript resources the React Native app imports today — with `git diff --exit-code`
in CI proving zero drift. That is the same pattern `scripts/gen-identicon-features.mjs`
already establishes, and it is why the app needs **zero source changes** (FR-011).

All decisions and measurements: [research.md](./research.md).

## Technical Context

**Language/Version**: Rust 1.97.1 (pinned by `rust/rust-toolchain.toml`), edition 2021, MSRV 1.85

**Primary Dependencies**: **none new**. Both candidates were measured and rejected — `icu_plurals` (57,960 wasm bytes, no `From<f64>`) and `phf` (largest artefact of all options, +18 transitive crates, 3.04 s cold build). `serde`/`serde_json` are already in `vela-core` and cover the runtime-JSON catalog path. `i18next@26.3.1` stays a **dev-time oracle** (already in `package.json`), never a runtime dependency.

**Storage**: N/A (pure computation). The corpus is committed JSON, relocated into the crate; the shared path table and per-locale catalogs are generated Rust source; the conformance corpus is committed JSON.

**Testing**: `cargo test -p vela-core` (conformance corpus + unit + proptest); an allocation-counting and latency benchmark mirroring `tests/identicon_bench.rs`; corpus generated by a standalone Node script driving the real `i18next` package; replayed on Kotlin/Swift/wasm by the existing harnesses.

**Target Platform**: `app-desktop` (direct Rust dependency), `app-ios`/`app-android` (uniffi 0.32), `app-web` (wasm32-unknown-unknown via wasm-bindgen). Also the current Expo/RN app's web path.

**Project Type**: library modules inside an existing multi-target Rust workspace, plus a Node generator

**Performance Goals**: < 1 µs per resolution (lookup + plural + two interpolations) with ≤ 2 heap allocations; < 0.5 ms for a 500-key screen; < 5 ms to load one catalog; lookup itself measured at 21.1 ns / 0 allocations, so the whole budget is available to plurals and interpolation

**Constraints**: no new runtime dependency; no host `Intl`/ICU dependency (FR-006); wasm artefact under 1,000,000 bytes (`rust/scripts/build-web.mjs:42`); no `unsafe` (crate-level `#![forbid(unsafe_code)]`); no `unwrap`/`expect`/`panic!` (crate-level `deny`); no unbounded mutable state (FR-024); translation files byte-for-byte unchanged (FR-009); the RN app unchanged except for consuming generated resources (FR-028)

**Scale/Scope**: ~1,400 lines across 6 new core modules + ~4 generated files; 15 locales; 1,205 key paths; 18,975 conformance cases; 5 new binding exports per surface

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

`.specify/memory/constitution.md` is still the unfilled spec-kit template — this
project has no ratified constitution. Applying spec-kit defaults in its spirit, and
the standing conventions features 001 and 003 established for this crate:

- **Library-first**: PASS — the modules are standalone and independently testable
  inside `vela-core`; binding exposure and any app migration come after they are green.
- **Test-first**: PASS — the 18,975-case corpus is generated from the real JS package
  and committed **red**, before the port is written. The corpus, not review, gates the
  work.
- **Simplicity**: PASS — no new crate, no new binding route, no new third-party
  dependency, no state. Two candidate dependencies were measured and both lost to
  hand-written code.
- **No hand-rolled primitives** (feature 001's FR-005, treated as a standing rule):
  PASS **with a recorded deviation**. CLDR plural rules and the `{{…}}` scanner *are*
  hand-rolled. The rule exists to stop hand-rolling *cryptography and numeric
  formatting*, where a subtle error is invisible; here the alternative was measured at
  48× the size, does not remove the hard part (`From<f64>`), and the hand-written
  version is validated against the authoritative oracle at 182,790/182,790. See
  Complexity Tracking.
- **Typed errors, never a default value** (feature 001's FR-004): PASS — FR-008 keeps
  the safe default strict; the two oracle throws become typed errors; bug-compatibility
  lives behind an explicit mode (FR-007), exactly as feature 003 did.
- **Byte-fidelity is proven by a committed oracle, not asserted**: PASS — FR-005,
  FR-027, D4.

**Structure Decision**: `i18n` and `l10n` are **directory modules**, not single files
like `identicon.rs`. The resolver alone has four genuinely separate concerns
(candidate-key ordering, plural selection, interpolation, catalog storage) that are
tested independently and fail independently; flattening them into one file would
produce a ~1,400-line module where a reviewer cannot tell which half of a diff is the
scanner. The two **generated** files (`paths.rs`, `i18n_catalogs/*.rs`) are separate
for the same reason feature 003 split `identicon_features.rs`: regenerating them is a
whole-file overwrite that can never disturb hand-written logic.

**The corpus moves into the crate** (`rust/crates/vela-core/i18n/locales/`) rather than
staying in `src/` and being copied. That is the requester's stated goal, and it makes
the direction of generation unambiguous: the crate is the source, every other artefact
— including `src/i18n/resources.ts` — is downstream and regenerable. Note this inverts
the repo's existing convention, where the crate has always been the *destination* of
codegen; the inversion is deliberate and is what "change one place, every platform
updates" requires.

## Phasing

The user stories are ordered so each is independently shippable.

| Phase | Delivers | Gate |
|---|---|---|
| 1 — Setup | error variants, module skeletons, cargo features | workspace builds on all 4 targets |
| 2 — Oracle | `i18n.dump.mjs`, 4 committed vector files, conformance wiring | corpus loads and is **red** |
| 3 — US1+US2 (P1) | resolver, plural, interpolation, catalog | all 18,975 cases green |
| 4 — US3 (P2) | corpus relocation + `gen-i18n.mjs` + generated `resources.ts` | RN app renders unchanged; `git diff --exit-code` clean |
| 5 — US4 (P2) | on-demand load/release, per-locale features and JSON assets | SC-005 residency measured; wasm under ceiling |
| 6 — US5 (P3) | `l10n/` — number, date/time, currency, bidi | `locale-format.ts` parity + CLDR currency matrix |
| 7 — US6 (P3) | benchmarks, proptests, binding exports, docs | SC-007/SC-008/SC-009 asserted in CI |

Phase 3 is the MVP. Phases 4–5 deliver the requester's "one place" and "on demand"
goals. Phase 6 is separable and could slip without blocking the rest.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Hand-rolled CLDR plural rules, against the "no hand-rolled primitives" standing rule | Hermes has no `Intl.PluralRules`, so the engine must own the rules or reproduce a known defect. 15 locales collapse to 5 rule bodies = 110 lines, 1,204 wasm bytes | `icu_plurals` measured **57,960 wasm bytes** — 48×, 12.35% of total headroom, +33 lock entries — and does **not** remove the hard part: `PluralOperands` has no `From<f64>` (E0277), so the f64→operands bridge is hand-written either way, plus a data-provider story. Validated at 182,790/182,790 against the authoritative oracle, which is a stronger guarantee than the crate's own test suite gives us |
| Hand-rolled `{{…}}` / `$t(…)` scanner instead of a regex crate | i18next's patterns are trivial and non-backtracking (`\{\{(.+?)\}\}`), and the workspace deliberately has no `regex` (typically ~1 MB of code against 469,220 bytes of headroom) | Adding `regex` would consume the entire budget for four fixed patterns. The scanner is ~80 lines and its behaviour is pinned by 210 behaviour vectors including unbalanced braces and duplicate placeholders |
| Two plural modes (CLDR + legacy `dummyRule`) instead of one | FR-005 wants MODE A as the target; FR-007 wants the parity claim provable against what natively ships today. **75 of 825** plural cases differ between them | A single CLDR mode makes the native-behaviour claim unverifiable and hides which 75 strings change on adoption. A single legacy mode bakes a confirmed defect into the shared core. Exactly the strict/bug-compatible split feature 003 already uses; the two differ by ~15 lines |
| Catalog split into a shared path table + per-locale value blob, instead of one flat map | Key bytes repeated per locale are 460,471 vs 31,198 interned — the flat array *fails* SC-005 at 138,309 for ja+en against a 135,345 budget | Flat `&[(&str,&str)]`: over budget and 781,054 bytes for all 15. `phf`: fastest but the largest artefact and +18 crates. `serde_json` tree: 2.6× over budget and 4 allocations per lookup. The split is the only option measured inside budget with 0 allocations |
| Web loads catalogs at runtime while native compiles them in — two paths, one resolver | Measured: all 15 compiled in is 315,023 bytes **over** a hard CI gate, and embedding is 1.33× worse over the wire than plain JSON. Native has no wire and no gate | A single compiled-in path fails the build. A single runtime path would force desktop and native to ship loose data files for no benefit. The cost is one `enum Values { Static, Owned }` — the resolver itself stays a single code path |
| The corpus moves *into* the crate, inverting the repo's codegen direction | The requester's core requirement: one edit, every platform updates. Keeping it in `src/` and copying makes the RN app the de-facto source and re-creates the drift this feature exists to end | Leaving it in `src/` was considered. It keeps the existing convention but means the crate can never be the authority, and every future platform would generate from a React Native app's internals |

## Risks

- **The generated `resources.ts` must be deep-equal, not just similar.** FR-011 is what
  makes "zero app changes" true. Mitigation: the generator emits it, and a test asserts
  deep-equality against the pre-move file before that file is deleted.
- **`Owned` catalogs need their own branch bitmap.** The D2 prototype reuses the
  compiled-in one, which is wrong for a runtime-loaded locale. Called out in
  research.md; must be closed in Phase 3, with a vector that exercises a branch node on
  a runtime-loaded catalog.
- **Adoption changes Russian strings on native.** Intended (SC-004), but it is a
  user-visible change and must be enumerated in the PR description, not discovered.
- **Two wasm-size traps are easy to reintroduce.** `&locale[..i]` slicing costs +28,553
  bytes (panic path pulls `core::fmt`) and f64 `%` costs +2,935 (software `fmod`). Both
  must carry a comment at the site, like feature 003's multiply-order note.
- **Nothing consumes `vela-core` on native today.** The near-term consumer is the web
  export plus future shells — the same position feature 003 shipped from. This is a
  scope fact, not a blocker, and FR-028 makes it explicit.
