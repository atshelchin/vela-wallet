## Phase 3: User Stories 1 + 2 — One exact implementation, correct plurals (P1) 🎯 MVP

**Goal**: `vela-core` reproduces `i18next@26.3.1` in MODE A byte-for-byte, and carries its own CLDR plural rules so ten Russian keys stop rendering the wrong grammatical form on every native build.

**Independent test**: `cargo test -p vela-core --features i18n-all` — all 18,975 cases green, with no app change of any kind.

### The generated tables (mechanical, and first because everything reads them)

`gen-i18n.mjs` is introduced here in its **crate-artefact half only**, reading the corpus at its current location `src/i18n/locales`. Phase 4 relocates the source directory and adds the `resources.ts` and per-locale-JSON stages. Splitting it this way is what lets the resolver be proven before the corpus moves — moving first would relocate strings without gaining confidence in how they render (spec US3 "Why this priority").

- [X] T014 [US1] Write `scripts/gen-i18n.mjs` stage 1: emit `rust/crates/vela-core/src/i18n/paths.rs` with `PATHS: &[&'static str]` (the **1,205** sorted paths = 1,141 leaf + 64 branch), `IS_BRANCH: &[u8]` (151 bytes, bit *i* = `PATHS[i]` is an object node) and `N_PATHS`. Assert and fail loudly on every invariant: strictly sorted, deduplicated, exactly 1,205 entries, **0 paths that are both leaf and branch**, and the path set identical in every locale. A silently partial table is the worst possible outcome. Header comment names the generating command, like `scripts/gen-identicon-features.mjs` does.
- [X] T015 [US1] `gen-i18n.mjs` stage 2: emit one `rust/crates/vela-core/src/i18n_catalogs/<lng>.rs` per locale — the concatenated value blob, a dense `&[u16]` offset array of `N_PATHS + 1 = 1,206` entries, and a 151-byte presence bitmap — each gated by its `i18n-<tag>` feature. **Offsets are `u16`, not `u32`, and the generator MUST assert `blob.len() < 65_536` per locale and fail loudly rather than truncate**: u32 puts 64-bit ja+en at 135,992, which is 647 bytes *over* SC-005's 135,345 budget, while u16 lands it at 131,168 on every pointer width (data-model.md correction 1; the largest blob, `ru`, is 57,701 with 7,835 bytes of headroom). **Never trim and never normalise** while flattening: 39 values are sentence fragments whose leading/trailing whitespace is concatenated at render time and zh/zh-TW/zh-HK deliberately omit it, so no uniform rule applies (D6/A6); all 240 files are already NFC, so re-normalising is a no-op that can only ever become a diff.
- [X] T016 [US1] Run the generator and commit `paths.rs` plus the fifteen `i18n_catalogs/*.rs`. Cross-check the emitted key blob against the measured 32,173 bytes (31,198 leaves + 975 branch paths) and the per-locale value blobs against data-model.md's residency table.

**Gate**: `paths.rs` and all fifteen catalogs compile under `--features i18n-all`, and the emitted counts match 1,205 / 1,141 / 64 exactly. Nothing below can be diagnosed against a table whose shape is wrong.

### Plurals (the part that justifies the feature)

- [X] T017 [US2] Implement operand extraction in `rust/crates/vela-core/src/i18n/plural.rs` per data-model.md "Operands, and the ×1000 scaling rule". Three instructions that are contract, each with a comment at the site: **(a) scale the whole value, never the fraction** — `s = round(n * 1000.0) as u64`, because `i = n.trunc()` then `round((n - i) * 1000.0)` produces 6 disagreements out of 15,810, all at `count = 1.0005` in en/tr/ru/es-MX/it/de, where `(1.0005 - 1.0) * 1000.0` is `0.49999999999994` and rounds to *v*=0 while ICU renders `"1.001"` (*v*=3); **(b) carry operands as `u64`, never `f64`** — wasm has no `f64.rem`, so every `%` calls `compiler_builtins`' `fmod` and drags in `__udivti3`/`__multi3`, measured at **+2,935 bytes**; **(c) the `is_finite` guard is load-bearing** — `f64 as u64` saturates, so `NaN` would otherwise become *i*=0 and select `one` under the fr/pt-BR rule.
- [X] T018 [US2] Implement the **five** CLDR rule bodies (`Other`, `OneOther`, `OneManyOther`, `OneZeroToOneManyOther`, `Russian`) and the `PluralCategory` enum with all six CLDR variants, per data-model.md's rule table. Comment it at the site, the way feature 003's `chaos_hash` carries "multiply order is contract, never `mul_add`".
- [X] T019 [US2] Implement `plural_category`, `plural_suffix` and `plural_suffixes` (contracts/i18n-api.md §5). `plural_suffixes` returns the CLDR-ordered list (`zero, one, two, few, many, other` — `i18next.js:1022-1029`), which is 4 distinct lists over the 15 locales and 29 reachable (locale, category) pairs. **`_zero` is i18next's, not CLDR's**: `needsZeroSuffixLookup` (`i18next.js:602`) adds `_zero` as an *extra* candidate when `count == 0 && !ordinal`. `plural_category` must return the true CLDR category — `other` for en/de/tr/it/es-MX, `one` for fr/pt-BR, `many` for ru — and let the candidate builder add `_zero` **on top**, never in place of it.

### Resolution

- [X] T026 [US1] Implement candidate-key construction in `rust/crates/vela-core/src/i18n/resolve.rs`. i18next **pushes** onto `finalKeys` (`i18next.js:823-852`) and **pops** (`:854-860`), so the actual try order is the reverse of the source order: `key_ctx_zero → key_ctx_plural → key_ctx → key_zero → key_plural → key`. **The bare key is a last resort, reached only after the plural-suffixed lookup misses** — that is the only reason the 11 corpus keys per locale that interpolate `{{count}}` with no plural siblings (defect A5, 165 entries) render at all. A port that tries the bare key first breaks 165 strings; a port that omits it breaks the same 165. At most 6 candidates, consumed strictly LIFO. Context is appended first and the plural suffix second, which is what disambiguates `key_male_other`; `needsPluralHandling` is `count !== undefined && !isString(count)` (`:809`), so `count: "3"` produces no plural candidate and `t('send.recipientCount', {count: '3'})` returns the raw key — reproduced, not repaired.

## Implementation notes

- **Do not "repair" the oracle while porting it.** The bare-key last resort, the
  per-fallback-code plural recomputation that leaks English for large numbers in four
  locales, the first-occurrence `String.replace`, the `{{var}}` left on screen, the
  `count: "3"` that returns the raw key, and `zh_TW` degrading to Simplified are all
  *current* behaviour. Each has a vector. Fixing any of them here makes the FR-005
  parity claim unverifiable and turns a reviewable change into an invisible one.
- **Do not fix the corpus.** FR-018 puts the six D5 defect classes out of scope: they
  are reproduced exactly, linted by T042, and filed separately.
- **Do not add a cache to the core** (FR-024), however tempting T060's benchmark makes
  it look. Caching stays at the caller, exactly as feature 003 decided for identicons.
- **Do not regenerate the vectors to make a diff go away.** Regenerating is correct only
  when the *oracle* or the *corpus* changed, and both of those are commits you can point
  at. A red conformance case is a release blocker: these vectors are what a user reads
  before authorising an irreversible transfer.
- **Two wasm size traps are easy to reintroduce**, and both read as ordinary Rust:
  `&locale[..i]` costs **+28,553 bytes** by linking the panic formatter, and an `f64 %`
  costs **+2,935** by calling a software `fmod`. Both sites carry a comment (T018,
  T017). If the module jumps by roughly either amount, that is what happened.
