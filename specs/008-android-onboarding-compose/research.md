# Research: Android Onboarding (Jetpack Compose)

**Branch**: `008-android-onboarding-compose` | **Date**: 2026-08-01

Numbered decisions, 007-style: **Decision / Rationale / Finding**. Findings come from direct inspection of the repo (file:line where load-bearing), the five-domain investigation pass, and the W1/W1L mocks.

---

## D1 — Kotlin binding consumption: committed bindings as a source dir, not a copy

**Decision**: The app consumes `rust/bindings/kotlin` (generated `uniffi.vela_core_uniffi` package, uniffi 0.32.0) directly via a Gradle `srcDir` pointing at the repo path. No copy into `app/src`, no `uniffi.toml` rename.

**Rationale**: The bindings are already committed, CI-smoke-tested (`.github/workflows/ci.yml` kotlin harness, kotlinc 2.1.0 + JNA 5.14.0), and checksum-coupled to the uniffi build. A copy would fork a generated file (violates the repo's generated-files-stay-generated rule); a `uniffi.toml` package rename would regenerate every consumer including the CI harness — out of scope per FR-011.

**Finding**: `rust/scripts/smoke-kotlin.sh` is the canonical generation recipe; `rust/harness/kotlin/Harness.kt:292-295` demonstrates the exact call sequence (`I18n(enBytes)` → `loadCatalog(tag, bytes)` → `changeLanguage(tag)` → `t(key, opts)`). The generated class needs `com.sun.jna` at runtime.

## D2 — Native library build: `cargo-ndk` via `rust/scripts/build-android.sh` + Gradle exec task

**Decision**: New script `rust/scripts/build-android.sh` cross-compiles `vela-core-uniffi` as cdylib for `arm64-v8a`, `armeabi-v7a`, `x86_64` into `app-android/vela-wallet/app/src/main/jniLibs/` (gitignored). A Gradle task `cargoNdkBuild` invokes it before `preBuild`; `-PvelaSkipRustBuild` skips it when the `.so`s already exist (or for IDE sync speed). `.so` artifacts are never committed.

**Rationale**: Mirrors the repo's existing per-platform build-script pattern (`build-web.mjs` for wasm, `smoke-kotlin.sh` for JVM). Committing multi-MB per-ABI binaries has no precedent for Android here (pkg-web's committed wasm is a web-deploy necessity, not a policy).

**Finding**: Local SDK has NDK 27.1.12297006 (`~/Library/Android/sdk/ndk/`); `cargo-ndk` and the three rustup Android targets are not installed — quickstart documents the one-time install. minSdk 31 → `--platform 31`.

## D3 — Locale catalogs: build-time copy from `public/i18n/`, no committed duplicates

**Decision**: A Gradle `Copy` task syncs the 15 merged per-locale JSONs from `public/i18n/*.json` (committed, generated by `scripts/gen-i18n.mjs`) into `build/generated/velaI18n/i18n/`, registered as an assets srcDir. Runtime loads `assets/i18n/<tag>.json`.

**Rationale**: `Catalog::from_json` consumes exactly the merged one-file-per-locale shape (per-namespace corpus files are NOT loadable directly). Copying at build keeps a single source of truth; corpus changes flow through `npm run gen:i18n` untouched by this feature (FR-011, SC-005).

**Finding**: All 15 files are committed under `public/i18n/` (verified with `git ls-files`). The engine errors on non-string leaves (`I18nCatalogParse`), so the merged files are the only safe input.

## D4 — Locale resolution: Kotlin-side ladder mirroring `resolve.rs`, engine-verified

**Decision**: A Kotlin `LocaleResolver` maps the system `LocaleList` to one of the 15 supported tags (`en, zh, zh-TW, zh-HK, ja, ko, vi, id, tr, es-MX, pt-BR, fr, de, ru, it`): per locale, try exact `language-region` tag → script-aware Chinese mapping (`zh-Hant` + TW/none → `zh-TW`, `zh-Hant-HK`/`zh-Hant-MO` → `zh-HK`, otherwise `zh`) → bare language → regional representative (`es→es-MX`, `pt→pt-BR`) → next locale in the list → `en`. Then `loadCatalog(resolved, bytes)` + `changeLanguage(resolved)`. A unit test cross-checks the resolver against the engine's own `LanguageState.resolvedLanguage` for the supported tags.

**Rationale**: The uniffi surface does not export `resolve_language` (`rust/crates/vela-core-uniffi/src/lib.rs` exports only the `I18n` object + interpolation/plural helpers), and `changeLanguage` performs no I/O — the host must decide which catalog file to load, so host-side resolution is unavoidable. Web set the same precedent (edge Worker does Accept-Language resolution outside the engine).

**Finding**: `SUPPORTED` lives at `rust/crates/vela-core/src/i18n/resolve.rs:30`; fallback is pinned `en`; max two catalogs resident (active + en), so one `loadCatalog` per language switch is the whole memory story.

## D5 — Token layer: hand-written Kotlin mirrors of `docs/design-tokens.json` + drift test

**Decision**: `core/designsystem/tokens/` holds hand-written immutable objects — `VelaColors` (light/dark instances), `VelaSpacing`, `VelaRadius`, `VelaType`, `VelaMotion`, `VelaSizing` — exposed through `LocalVela*` CompositionLocals by `VelaTheme`, which also maps the palette onto a Material3 `ColorScheme` (dynamic color off) for the M3 components used (Scaffold, ModalBottomSheet, ripple). A JVM unit test parses `docs/design-tokens.json` (path `../../../docs/design-tokens.json` from the app module) and asserts every Kotlin color/dimension equals the export — the FR-005 drift gate.

**Rationale**: 007 hand-rolled `Theme::of(mode)` palettes with checklist verification; the drift test is strictly stronger (executable, runs in `testDebugUnitTest`). Codegen from DTCG would be new infrastructure for one consumer — not justified at this scope.

**Finding**: The export has 147 tokens in sets `core` + `color-light` + `color-dark`; the WCAG-corrected values (`fg.muted #6E6B62` light, `fg.subtle #85827A` dark, `error.base #C62828` light) supersede the stale hexes in `DESIGN_SYSTEM.md`.

## D6 — Fonts: bundle the repo's Plus Jakarta Sans TTFs; CJK via system fallback (DV-003)

**Decision**: Copy `PlusJakartaSans-{Regular,Medium,SemiBold,Bold}.ttf` from `packages/safe-recovery-extension/public/font/` into `app/src/main/res/font/` and build a `FontFamily` with weights 400/500/600/700. No Noto Sans SC bundle; CJK falls back to the system font (spec DV-003).

**Rationale**: The four exact weights the type scale requires already live in the repo (OFL-licensed, same family the RN app ships). Noto Sans SC would add tens of MB for a v1 with a system-provided equivalent (Source Han Sans), the same trade 007 recorded.

**Finding**: Weight→file mapping is mandatory on Android (the design-system carry-over note): 400→Regular, 500→Medium, 600→SemiBold, 700→Bold.

## D7 — Navigation: `androidx.navigation:navigation-compose` (stable), three destinations

**Decision**: `navigation-compose` 2.9.x with routes `welcome`, `create`, `import`; both CTAs dispatch through a typed `OnboardingIntent` sink in the ViewModel which requests navigation (single-shot, guarded against double-tap re-entry).

**Rationale**: Navigation3 is too new to anchor the app's first slice; navigation-compose is the boring stable choice and trivially replaceable later. The intent sink matches 007 FR-010 and gives the future create/import flows a seam.

## D8 — State: minimal ViewModels, manual composition root, no DI framework

**Decision**: `MainViewModel` (theme preference StateFlow + i18n readiness), `WelcomeViewModel` (intent sink, settings-sheet visibility). Carousel page = `rememberPagerState` (self-restoring). Dependencies wired in a hand-rolled `AppContainer` created by the `Application` class.

**Rationale**: Two ViewModels do not justify Hilt/Koin; the brief asks for clear layering, which a composition root delivers with zero magic. Engine init (read `en.json` asset + construct `I18n`) is cheap enough for `Application.onCreate` off the main thread with a ready-flag.

## D9 — Theme persistence: `androidx.datastore:datastore-preferences`

**Decision**: DataStore Preferences stores `theme_preference` (`light`|`dark`|`auto`, default `auto`); exposed as `Flow<ThemePreference>`, collected in `MainActivity` before/behind the splash.

**Rationale**: DataStore is the current-platform default; SharedPreferences is legacy. The single-value store stays in `core/data` so later settings (endpoint URL, text scale) join it without re-architecture.

## D10 — Splash & window theming: core-splashscreen, fixed `#1A1A18`

**Decision**: `androidx.core:core-splashscreen` with `windowSplashScreenBackground = #1A1A18` (`color.fixed.splashBg`, both modes), post-splash theme a DayNight-correct NoActionBar theme; `themes.xml` loses its Light-only parent.

**Rationale**: FR-006; the token export pins splash to dark ink in both modes, so the splash theme is a single fixed style while the app content theming is entirely Compose-side.

## D11 — Placeholder copy: existing corpus keys only, no new keys

**Decision**: The Create placeholder titles itself with `onboarding.create.headerTitle`, the Import placeholder with `onboarding.welcome.alreadyHaveWallet`; back affordance is an icon (ArrowLeft, content-described by `common.back` if present, else the icon's decorative role is documented). No body copy if no suitable existing key exists — a placeholder needs a title and a way back, nothing more.

**Rationale**: FR-011 forbids corpus edits; minting 15-locale keys for throwaway placeholder prose is exactly the kind of scope creep the discipline exists to stop. 006's placeholders are equally minimal.

**Finding**: To be confirmed against `locales/en/{common,onboarding}.json` during implementation; the fallback (title + back icon only) is acceptable under FR-002.

## D12 — Press feedback: Material ripple + spring scale approximation

**Decision**: CTAs combine the M3 ripple with a press-scale animation to 0.97 driven by `animateFloatAsState` + `spring(dampingRatio = 0.75f, stiffness = 600f)`; cards/rows use ripple only.

**Rationale**: The design system mandates spring-based interactive feedback (RN Reanimated damping 15 / stiffness 150 / mass 0.8). Reanimated and Compose spring parameters are not unit-compatible; the chosen Compose values reproduce the perceptual behavior (fast settle, no oscillation). Recorded as an approximation, not a token.

## D13 — Welcome layout: mock-derived metrics on the 390×844 frame

**Decision**: Screen padding 24 dp (`layout.screenPaddingX`); brand block (mark 56 dp + wordmark `text.4xl`-zone bold) centered at ~27% height; tagline `text.xl` regular, `fg.muted`; card = `bg.raised`, `radius.xl` 16 dp, internal padding 20 dp, ordinal `text.sm` `fg.subtle`, title `text.2xl` semibold, body `text.lg` regular `fg.muted`, `leading.normal`; pager dots 8 dp (active pill-widened, accent) with ≥24dp hit areas; primary CTA height 52 dp (`sizing.control.lg`) accent pill, label `text.lg` semibold white; secondary CTA height 52 dp outlined (`border.base` 1 dp), label `fg.base` (DV-001); 12 dp between CTAs, bottom inset respected (edge-to-edge).

**Rationale**: All values are existing tokens; the mock (784×1688 = 2× 392×844) was sampled for proportions, not new pixel values — the brief forbids inventing off-grid values.

## D14 — Test seam for the native engine on the JVM

**Decision**: Unit tests run against the real engine through the host-platform dylib: a Gradle exec task builds `libvela_core_uniffi.dylib` (`cargo build --release -p vela-core-uniffi`) when absent, and `testDebugUnitTest` sets `jna.library.path` to `rust/target/release`. `testImplementation(net.java.dev.jna:jna)` (plain jar) complements the runtime `@aar`.

**Rationale**: Spec 005's native-adoption verdict requires the native rollout to carry its own differential evidence; a mocked i18n interface would test nothing real. This reuses the exact mechanism the CI kotlin harness already proves works on macOS/Linux JVMs.

**Finding**: CI installs JNA 5.14.0 jar for the harness; the same version goes in the version catalog.

## D15 — Stale scaffold dependency pins: bump only what this feature touches

**Decision**: Bump `activity-compose` and `lifecycle` to current stable, add `lifecycle-viewmodel-compose`, `navigation-compose`, `datastore-preferences`, `core-splashscreen`, `jna`; leave `core-ktx` and test libs as-is unless the build complains; keep `material3-adaptive-navigation-suite` out of the dependency list for this feature (phone-only brief — the template's adaptive scaffold gets deleted with `MainActivity`'s stub content).

**Rationale**: Minimal-churn discipline (FR-011): the diff should read as "onboarding feature added", not "template refreshed". The 2023-era pins under a 2025.12 BOM are latent tech debt but only blocking pieces get touched.
