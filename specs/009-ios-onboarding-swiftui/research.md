# Research: iOS Onboarding in SwiftUI

Decisions D1–D10. Each records what was chosen, why, and what was rejected.

## D1 — Token pipeline: generator + committed Swift output + drift gate

**Decision**: New `app-ios/scripts/gen-tokens.mjs` reads
`docs/design-tokens.json` (the canonical Penpot DTCG export; sets `core`,
`color-light`, `color-dark`) and emits
`app-ios/VelaWallet/VelaWallet/DesignSystem/Tokens.swift` — committed, with a
`--check` mode that regenerates to a temp buffer and diffs (exit 1 on drift).
Values the export lacks live in one `IOS_ADDITIONS` block inside the generator,
each entry citing the `design-system.md` line that licenses it — initially:
control heights 36/44/52 (`sizing.control.*`), `color.onAccent = #FFFFFF`
(both modes, web precedent), and the typography role recipes (D8).

**Rationale**: Byte-for-byte the pattern spec 006 proved
(`app-web/vela-wallet/scripts/gen-tokens.mjs` + committed `tokens.css`/`.ts` +
check gate). The export, not `design-system.md` prose and not desktop's
`theme.rs`, is the stated value authority; 007's hand-sampled palette
deliberately deviates and MUST NOT be copied (its dark `bg_sunken`,
`fg_inverse`, border values differ from the export).

**Alternatives rejected**: hand-written Swift palette (what desktop did —
already drifted); Xcode asset-catalog colorsets (values leave the reviewable
text pipeline, no single-file drift gate); consuming Penpot MCP at build time
(network dependency; the committed export exists precisely to avoid this).

## D2 — vela-core consumption: XCFramework + local Swift package

**Decision**: New `rust/scripts/build-ios-xcframework.sh`:
1. `cargo build --release -p vela-core-uniffi` (host dylib — binding source);
2. `cargo run --release -p vela-core-uniffi --bin uniffi-bindgen -- generate
   --library target/release/libvela_core_uniffi.dylib --language swift
   --out-dir …` (exactly `smoke-swift.sh`'s invocation);
3. `cargo build --release -p vela-core-uniffi --target aarch64-apple-ios` and
   `--target aarch64-apple-ios-sim` (staticlib slices);
4. `xcodebuild -create-xcframework` from the two `libvela_core_uniffi.a` +
   headers dir (`vela_core_uniffiFFI.h` + `module.modulemap`) →
   `app-ios/VelaCoreKit/Artifacts/VelaCoreFFI.xcframework`.

Consumed through a local Swift package `app-ios/VelaCoreKit`:
`.binaryTarget` on the XCFramework + a `VelaCore` target holding the generated
`vela_core_uniffi.swift`. The generated `.swift` is **committed** (reviewable,
diffable — same philosophy as the committed `rust/pkg-web` wasm bindings); the
XCFramework binary is **gitignored** and rebuilt by the script (tens of MB of
static libs don't belong in git; `rust/pkg-web`'s committed artefact is ~2 MB
wasm, not a precedent for 40 MB of `.a`).

**Rationale**: uniffi 0.32 proc-macro bindings already exist and are CI-checked
(`smoke-swift.sh`, ci.yml); the only missing piece is app-consumable packaging.
A local SPM package needs exactly one pbxproj change (package dependency) and
keeps the FFI module (`vela_core_uniffiFFI` via modulemap) out of the app
target. Both rustup targets are installed on this machine (sim was present;
device target added during planning).

**Alternatives rejected**: committing the XCFramework (size, opaque binary
churn per Rust change); dragging the generated swift + `.a` straight into the
app target (modulemap import breaks under file-sync groups; mixes layers);
building vela-core with cargo feature `i18n-all` and `Catalog::embedded` (needs
no JSON files but bakes 15 catalogs into every future binary consumer; the
runtime-JSON route (D3) matches how iOS will later want lazy locale data);
CocoaPods (nothing else in app-ios uses it).

## D3 — Catalogs: bundle the committed `public/i18n/*.json`, synced + checked

> **SUPERSEDED by spec 010-ios-catalog-bundling (2026-08-02).** The runtime-JSON
> route below still stands; what changed is how the JSON reaches the bundle. The
> 15 committed copies under `Localization/Catalogs/` and `sync-catalogs.mjs` are
> deleted — an Xcode script phase now copies `public/i18n/*.json` straight into
> `VelaWallet.app` at build time, matching Android's Gradle `Sync` task, and the
> `--check` drift gate is replaced by
> `node app-ios/scripts/gen-catalog-filelists.mjs --check`. The "folder
> reference" alternative rejected at the end of this decision was *not* what 010
> adopted; see 010's research D1–D3. The text below is kept as the record of
> what was true for spec 009.

**Decision**: `app-ios/scripts/sync-catalogs.mjs` copies the 15 merged runtime
catalogs from `public/i18n/<lng>.json` (generated by `scripts/gen-i18n.mjs`,
already committed) into
`app-ios/VelaWallet/VelaWallet/Localization/Catalogs/`, with `--check` diffing
byte-for-byte. The app constructs the engine with
`I18n(fallbackJson: en.json bytes)` and `loadCatalog(lang:, json:)` for the
resolved locale — the uniffi mirror of web's `Catalog::from_json` route.

**Rationale**: `gen-i18n.mjs` stays untouched (FR-011); the copy is itself
drift-gated so the corpus remains single-source. Verified during planning:
`public/i18n/en.json` contains the full `onboarding` namespace, and
`zh/onboarding.json`'s `welcome.desktopTagline` = 「您的密钥，您的资产」—
exactly the W1 mock string, confirming the FR-006 key choices:
`onboarding.welcome.desktopTagline` (tagline),
`onboarding.welcome.feature{NoMnemonic,OneAddress,OpenSource,KeyCustody,SafeContract,StablecoinGas}{Title,Body}`,
`onboarding.welcome.createWallet`, `onboarding.welcome.alreadyHaveWallet`.

**Alternatives rejected**: Xcode folder reference into `../../public/i18n`
(reaches outside the app-ios tree; fragile across checkouts and confuses the
synced-group model); editing `gen-i18n.mjs` to emit into app-ios (touches the
shared pipeline all other platforms regenerate from — scope risk); compiled-in
catalogs (see D2).

## D4 — Deployment target: iOS 17.0

**Decision**: Lower `IPHONEOS_DEPLOYMENT_TARGET` from the template's 26.2 to
**17.0** for all targets.

**Rationale**: 26.2 is the newest OS — a wallet for real devices cannot
require it (spec assumption). iOS 17 is the floor for the APIs this
architecture standardises on: `@Observable` models, `NavigationStack` typed
routes (16+), `scrollTargetBehavior(.paging)`/`containerRelativeFrame` if the
carousel needs them. Nothing in scope needs 18+.

**Alternatives rejected**: keeping 26.2 (excludes almost every device);
matching the Expo app's 15.1 floor (forfeits `@Observable`, buys nothing —
the native app has no install base to preserve).

## D5 — Fonts: bundle Plus Jakarta Sans static TTFs from the repo

**Decision**: Copy `PlusJakartaSans_{400Regular,500Medium,600SemiBold,700Bold}.ttf`
plus `LICENSE_FONT` (OFL) from `node_modules/@expo-google-fonts/plus-jakarta-sans/`
into `DesignSystem/Fonts/`, register via `UIAppFonts` in the partial
`Info.plist` (merged by `GENERATE_INFOPLIST_FILE=YES`). PostScript names
verified at implementation time and centralised in `Typography.swift`. CJK
text falls through to the iOS system face (PingFang SC) — DV-003, identical to
the shipped RN app, which loads exactly these four weights and lets CJK fall
back.

**Rationale**: the files already live in the repo's dependency tree (no new
download), are OFL-licensed, and are the exact binaries the RN app renders
with today. `@fontsource` (web's source) ships only woff/woff2, which
`UIAppFonts` cannot register.

**Alternatives rejected**: bundling Noto Sans SC (~10 MB+ for a fallback the
platform already provides well); full system-font stack (007's DV-003 route —
but unlike desktop, mobile has the exact brand TTFs available and web already
ships them); variable-font TTF from google/fonts (network fetch + named-
instance registration quirks for zero gain over the static weights).

## D6 — Locale resolution: port `shared.ts` semantics onto `Locale`

**Decision**: `Loc.swift` resolves from `Locale.preferredLanguages.first`
using the same mapping as `src/i18n/shared.ts#detectSystemLanguage` (which 006
copied verbatim for web): `zh` → script `Hant` ? (region HK/MO → `zh-HK` else
`zh-TW`) : `zh`; `es-*` → `es-MX`; `pt-*` → `pt-BR`; legacy `in` → `id`; exact
supported tag wins; base-language match next (`fr-CA` → `fr`); otherwise `en`.
The result feeds `changeLanguage` on the engine; `LanguageState.resolvedLanguage`
is the single source of truth afterwards. A `VELA_LANG` launch
environment/argument overrides detection (D7).

**Rationale**: three platforms already agree on these semantics; iOS diverging
on `zh-Hant-HK` or `es-AR` would produce cross-platform locale mismatches.
`vela-core`'s own `resolve_language` is deliberately asymmetric (bare `ZH` →
`en`), so pre-mapping on the app side — as web and RN both do — is required,
not optional.

**Alternatives rejected**: `Bundle.preferredLocalizations` (would require
declaring iOS localizations and hands control to UIKit's matcher — a second,
subtly different negotiation); sending raw BCP-47 tags into the engine
(documented to fall to `en` for e.g. `zh`).

## D7 — Theme + test overrides

**Decision**: The active palette follows SwiftUI's `colorScheme` environment
(system appearance, live switching for free). For SC-002/SC-004 verification,
the app honours two launch overrides read in one place at startup:
`VELA_THEME=light|dark` (applies `preferredColorScheme`) and `VELA_LANG=<tag>`
(bypasses D6 detection) — the same override names 007 standardised, wired as
`ProcessInfo` environment/launch arguments so `xcrun simctl launch` and UITests
can set them.

**Rationale**: dark/light parity is a P1 acceptance criterion; screenshots
must be forcible without touching simulator global state. Reusing 007's names
keeps the cross-platform verification recipe uniform.

**Alternatives rejected**: UI toggles (spec Out-of-scope), simulator-wide
appearance flips per shot (slow, leaky between runs).

## D8 — Typography roles + geometry source

**Decision**: `Typography.swift` defines the `design-system.md` roles
(`display`, `title`, `body`, `label`, `button`) as complete recipes composed
from generated core scales (`text` 10/11/13/15/17/20/26/32/40, `weight`
400–700, `leading` 1/1.2/1.4/1.6) — role mapping mirrors what W1 needs:
display 32/700 (wordmark), title 20/600 (card title), body 15/400×1.4 (card
body, tagline at 17), label 13/500 (card numeral), button 17/600. Text
respects system Dynamic Type by scaling relative to these token sizes
(`@ScaledMetric`-style), per the founder's standing "keep native OS scaling"
direction; the app-level six-step text-scale setting stays out of scope.
Layout geometry comes from the tokens where they exist (screen padding 24 =
`layout.screenPaddingX`, card radius 16 = `radius.xl`, design frame 390×844 =
`layout.frameW/H`, CTA height 52 = `sizing.control.lg`, pill buttons per
006's radius decision) and from measuring W1 at 390 pt for the rest (card
height band, dot size/gap) — recorded as named constants in `Theme.swift`'s
additions block, never inline.

**Rationale**: the export ships no `typography.*` composites (known gap — web
solved it the same way, licensed by design-system.md rule 3); the mock is the
only authority for per-screen geometry the token set doesn't name.

## D9 — Xcode project surgery (one-time, minimal)

**Decision**: In `project.pbxproj`: deployment target 17.0 (D4),
`TARGETED_DEVICE_FAMILY=1`, add the local `VelaCoreKit` package dependency +
product. Delete the SwiftData template code (`Item.swift`, template
`ContentView.swift` body) — the app has no persistence. Trim
`VelaWallet.entitlements` to an empty dict (template claims push + CloudKit
with no backing capability; unused claims can break automatic signing on
other machines). `UIAppFonts` goes in the partial `Info.plist` (the file
`GENERATE_INFOPLIST_FILE` merges), not a full plist replacement. Everything
else (new sources, fonts, catalogs) lands on disk under the synced group —
zero per-file pbxproj entries. The `SWIFT_DEFAULT_ACTOR_ISOLATION=MainActor`
setting stays: UI code benefits, and the generated bindings compile inside
`VelaCoreKit` (its own package, default isolation) so they are unaffected.

**Caution carried from planning**: anything dropped under
`VelaWallet/VelaWallet/` enters the app bundle — scripts and docs must live
outside the synced tree (hence `app-ios/scripts/`).

## D10 — Test strategy

**Decision**: Swift Testing (template's unit target) for: D6 mapping table
(the `shared.ts` cases as fixtures, incl. zh-Hant-HK/es-AR/in/unsupported),
carousel/pager state (index clamping, no wrap), engine smoke (en fallback +
zh catalog load, key-echo detection on a known key), and SC-005 contrast
(relative-luminance from the generated token values, 4.5:1 floor, 3.0:1 for
the DV-004 accent pairs and DV-001 secondary label). SwiftUI Previews for
every component in both schemes. Script gates run from the repo root:
`gen-tokens.mjs --check`, `gen-catalog-filelists.mjs --check` (spec 010; was
`sync-catalogs.mjs --check`), and a literal audit
(`rg` for hex/`Color(red:`/point literals outside `DesignSystem/`). Screenshot
matrix via `xcrun simctl` + D7 overrides, compared against W1/W1L (SC-002).

**Rationale**: matches 007's executable-contrast + screenshot-matrix pattern
and the spec's FR-012; UITest automation of paging gestures is deliberately
thin (one launch smoke) — gesture fidelity is covered by state tests +
manual/screenshot passes, not flaky scroll simulation.
