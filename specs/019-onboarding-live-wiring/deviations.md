# Deviations & follow-ups — spec 019 implementation (2026-08-25)

Everything that diverged from the design, the contracts or the task list, in the shape
spec 014 established. Items marked ⚠ need a founder decision or a later feature; unmarked
items are documented-and-accepted.

---

## 1. Eighteen outcome kinds became nine prompts and five screens

**Research D13 said** spec 014's eighteen `OutcomeKind` values would be re-skinned rather
than reduced. Their COPY was re-skinned — every corpus key survives — but **eight of them
are no longer sheets**, on all four clients, because v2 gave them somewhere better:

| 014 outcome | Where it is in v2 |
| --- | --- |
| `Created` | the Done screen |
| `SignedIn` | the wallet itself |
| `SyncFailed` | the Retry screen, with the whole key list intact |
| `VerifyStuck` | the Name screen, with the 完成验证 submit label |
| `CancelledSetup` / `CancelledVerify` / `LoginCancelled` | the Name screen's quiet status line |
| `AccountNotFound` | a `sign_in_failed` prompt carrying the registry's own words |

Keeping all eighteen as sheet variants would have meant eight enum arms nothing
constructs — and, worse, would have kept 014's premise that a cancellation with a
filled-in form behind it is a modal. `data-model.md §5` already says it is not, and the
Android device run confirmed the v2 behaviour reads correctly: cancelling the system
passkey sheet lands back on the Name screen with the form intact and a one-line
"设置已取消。" status.

## 2. The spec-014 presentation types are deleted, not adapted

`CreatePanelState` / `LoginPanelState` / `OutcomeSpec` / `FlowAction` / `ActionId`'s
twenty-three cases are gone from Android and iOS (and were never on desktop or web).

They were a second model of one flow, and **the gallery drove them while the app drove
nothing at all** — which meant a fixture could look right in the gallery and wrong in the
app, with no test able to notice. Every fixture now goes through the same `screenFor` the
app does. Two fragments survived on iOS because both are genuinely the shell's:
`ActionId` (two cases, routing an inline link tap inside `AckRow`) and `TechDetails` (the
disclosure's runtime-diagnostics shape).

## 3. `rust/bindings/` cannot be committed (T097)

T097 asks for `rust/bindings/swift/` and `rust/bindings/kotlin/` to be committed. They are
**gitignored by an existing repo rule** (`rust/.gitignore:2 bindings/`), as is
`app-ios/VelaCoreKit/Artifacts/` (`app-ios/.gitignore:30`) — all are build outputs
regenerated by the two build scripts. The one generated file that *is* committed,
`app-ios/VelaCoreKit/Sources/VelaCore/vela_core_uniffi.swift`, carries the new classes and
is in this feature's commits. The task text assumed a layout the repo does not have.

**The gitignore is right and the drift it invites is real**: the Android emulator caught
an `UnsatisfiedLinkError` at launch because the packaged `.so` predated the three new
`registry_*` functions while the generated Kotlin already called them, and the identical
drift appeared on iOS an hour later. ⚠ Worth a build-time symbol check, or making
`-PvelaSkipRustBuild` refuse when the Rust tree is newer than `jniLibs`.

## 4. `Package.swift` says `.iOS("17.4")`, not `.iOS(.v17_4)` (T125)

T125 specifies the enum case. It needs a newer `swift-tools-version` than the package
declares, and raising the tools version would also switch the default Swift language
mode — a Swift 6 strict-concurrency migration is not something to take on as a side
effect of a deployment-target bump. The string form is the same constraint. Both halves
still moved together, which is what the task is actually about.

## 5. The iOS entitlements file was empty — a blocker, found by T138

`VelaWallet.entitlements` contained `<dict/>`. Without `com.apple.developer.associated-domains`
the passkey provider refuses every ceremony for `getvela.app`, so the entire feature would
have been inert on a device while building and passing tests perfectly. The
apple-app-site-association half was already live and correct (`200`, `application/json`,
this bundle id under `webcredentials`); only the app's half was missing. Now:
`webcredentials:getvela.app` and `applinks:getvela.app`.

## 6. The Android consent row's links moved out of the sentence

The web and iOS clients render the two policy links INSIDE the consent sentence. On
Android the checkbox row is a single touch target (`VelaAckRow`'s `toggleable`), so an
inline link either steals the tap or is too small to hit — the spec-011 lesson that
component already carries. The first pass coloured the phrases accent-orange anyway,
which the emulator showed for what it was: **a link that looks tappable and is not**, on
the one row a person is being asked to agree to. They are emphasis now, and a separate
quiet row is where the documents actually open. iOS keeps them inline because `AckRow`
there disables row-wide toggling when a row has links.

## 7. `CreateView` fixtures are the state set; there are no login fixtures

Spec 014 had a `login` gallery group with six states (`B1`…`B6`). `LoginView` is two
booleans (`data-model §4`) and everything else a person sees during sign-in is a prompt or
the wallet — so the login group's states now live in the Failures group as prompt kinds.
The gallery has thirteen flow steps and nine prompts, on Android, iOS and desktop alike.

## 8. Progress is three segments, not five

Spec 014's flow bar had five. Those counted the internal STATUS steps of a single derive —
a fact about the machine rather than about the person's progress through it. v2's bar has
three (name, keys, everything after), and the internal steps are the progress SCREEN's
three task rows, where they belong. The elapsed-seconds ring is gone from the create flow
entirely (research D9), which also retires spec 014's ⚠ "unify the ring sweep across
platforms" follow-up.

## 9. Not verified, and what was checked instead

### T089 / T091 — desktop, against a security key

**Still blocked**: this build host has no FIDO2 key. Phase 5's hardware session (see
`results.md`) covered sign-in on a real authenticator and four bugs came out of it; the
remaining list in "Still unverified" stands, unchanged.

### T119 / T121 / T142 — the two device sweeps

- **Android**: run on an API 34 Play-Store **emulator**, not the `alioth` phone — no
  physical device was attached to this host. What the emulator proved is nonetheless the
  load-bearing half: the WebAuthn JSON this client builds is accepted by the real
  Credential Manager, the wallet name reaches the system sheet, the status line and the
  cancel-recovery path behave as `data-model §3/§5` specify, and every gallery fixture
  renders. What it could NOT prove is a completed registration — the emulator has no
  enrolled passkey provider, so Credential Manager offers only the hybrid QR path.
  ⚠ **A completed create, and therefore T119's one-signature sign-in, needs the phone.**
- **iOS**: the app builds, installs, launches and stays alive on the iOS 26.2 simulator
  (PID alive, no crash report), and 107 unit tests run inside that simulator. The
  simulator's **display never rendered** on this host — `simctl io screenshot` returned the
  springboard across a SpringBoard restart and a full device erase — so there is no visual
  confirmation of any iOS screen. ⚠ **Every iOS screen is unverified by eye.**

### T145 — cross-client address agreement, done differently and more strongly

The task asks for a multi-key wallet created on one client and signed into on the other
three. The property behind SC-003 is not really about four devices: all four clients derive
the address by calling `compute_safe_address_multi` in `vela-core`, so what has to agree is
the four **surfaces** that one function is reached through. Four people with four phones
would be testing the same function four times and calling it evidence.

So the golden multi-key Safe is now pinned in all four:

| Surface | Result |
| --- | --- |
| Rust (`app-desktop` links `vela-core` directly) | `0x88cCA0EeDbF2C4426110bbFc998F048689266894` |
| wasm (`app-web`, browser extension) | same — `src/__tests__/services/passkey-fixture.test.ts` |
| uniffi Kotlin (`app-android`) | same — `rust/harness/kotlin/Harness.kt` (new) |
| uniffi Swift (`app-ios`) | same — `rust/harness/swift/main.swift` (new) |

A derivation change is now a conscious edit in four places rather than a silent drift in
one. ⚠ The end-to-end walk (create here, sign in there, read the address off four screens)
still wants doing once real hardware is available — it would catch a *storage* or *wire*
divergence this check cannot.

## 10. `withAddress` — the one non-fixture thing on the wallet home

The wallet home is still spec 015's fixture layer, with one exception on Android and iOS:
the header's address and identicon seed come from the session. An address is the one thing
on that screen a person acts on, and showing a fixture address after a real create would be
the app telling them their money is somewhere it is not. Everything else there is
visibly-placeholder balance data; an address is not. ⚠ The rest of the home screen is still
fixtures and is a later feature's job.
